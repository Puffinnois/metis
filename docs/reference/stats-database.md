# Stats database: data reference

Each league's stats are one DuckDB file beside `metis.db`: `stats-nba.duckdb` holds every table the NBA dataset publishes, every season (D36; "Leagues" below). Deleting a league's file makes its next refresh rebuild it. What the files are and what was measured about them is in [nba-data-sources.md](nba-data-sources.md); which seasons really hold values is in [nba-coverage.md](nba-coverage.md).

## Leagues

Metis covers more than one league (D34) and shows one at a time (D35). This section is the mechanism every later part builds on. **The rule: read what differs by league from the registry; pass the league; never branch on a league's id outside the registry.** Do not add a `league` column to a table, a module-level "current league" in the main process, or an `if (league === 'wnba')` anywhere: add a field to the registry and read it.

### How the league reaches each part

- **The worker.** One worker per league with something to read (`createLeagueControl` in `src/main/stats/leagueControl.ts`, see "Which leagues download"), started with `StatsWorkerInit { league, dataDir, tempDir }`. It resolves `leagueOf(init.league)` once and that entry is its context for everything it serves. A league that is off and has no file gets no worker and no file. Rule 3 holds per file: writes in turn, each read on its own connection. Each worker spills to `<userData>/stats-tmp/<league>/` and has DuckDB's 1 GB limit. **A worker opens when something needs its league and closes when idle** (`src/main/stats/workerPool.ts`, D22's addition of 2026-11-22): a read, a refresh or a links step opens it and holds it while it runs; with nothing using it for 60 seconds it closes, if its league is not on screen (the window names it, `api.leagues.onScreen`), or if it is but has refreshed with rows written since it opened, since a finished load leaves memory in the process that only closing the worker gives back. An open waits for the league's last worker to close, so a file never has two; a closed league's status is the one it gave as it closed, so the window reading it opens nothing. The links worker closes when idle the same way. A four-league first load in one session peaked at 4.77 GB before and 3.08 GB with it; a switch to a league whose worker had closed answers its first board in about 0.7 s (Plan, Stage 13 gate).
- **The service and sync.** `openStatsService` passes the league to `refreshStats` (`StatsSyncDeps.league`, with the league's `SOURCES_BY_LEAGUE` entry), which reads `league.currentSeason(now)` and hands the league to the builders.
- **The builders.** A play builder's `select(have, season, league)` and a model's `ModelContext.league` carry it; `buildPlays(db, league)`, `buildModels(db, current, league)`, `buildIdentity(db, league)`, `bootstrapStatsDb(db, now, league)` take it. A builder reads what differs from the entry (a period's length in that season), never from the id. Which builders run at all is the entry's `builds` (next section). A league without `derived` (the WNBA until T1301.6) logs one `stats:derived` step as `skipped` with the reason when its refresh wrote anything (`notBuilt` in `sync.ts`), and its worker answers every screen's read with `League.notBuilt`, through `offlineStats(league, reason)`, never an error; its status carries the reason as `noData`.

### How each league's tables are built

Two registry fields, one mechanism, decided for T1301.5 so that each later part turns on its own tables without touching it:

- **`builds`** lists the built tables a league has, as steps of its refresh, in `BUILT_TABLES` order: `identity` (`game`, `team`, `player_ids`, `player`), `derived` (the game and season tables), `published`, `plays`, `models`. `refreshStats` runs a step only when `builds(league, step)` holds, and otherwise exactly as before; the service serves the engine and the screens only once the league has `derived`. The NBA lists all five. The WNBA lists `identity` alone: T1301.6 adds `derived`, T1301.7 `published` and `plays`, T1301.8 `models`, each by adding its step to the WNBA's entry and making its builders read the league's tables.
- **`identity`** names the recipe that builds the identity tables (`IDENTITY_RECIPES` in `src/main/stats/identity.ts`): `nba` reads the NBA's schedule and box scores, `wnba` the WNBA's schedule, game logs and 2026 box scores (`identityWnba.ts`). A recipe is `{ version, needs, build(db, league) }`. Every recipe writes the same tables with the same columns and meaning, so the builders, the engine and the screens after it read them unchanged; a recipe may add columns at the end, never change one. The SQL the recipes share stays in one place (`identityShared.ts`: the name key, and the matching of ESPN's players to the league's ids, over the league's lines); only what differs between the leagues' sources is written per recipe.
- **Versions are per recipe.** `derived_state('identity')` holds the version of the recipe that built the file, and `identityStale(db, league)` compares it with that league's recipe, so changing the WNBA's recipe never rebuilds the NBA's tables, and the reverse. `IDENTITY_NEEDS`, the tables whose releases can never be left out (`leftOut.ts`), is every recipe's needs together.
- **`derived`** names the recipe that builds the game tables, on the same pattern (T1301.6): `DERIVED_RECIPES` in `src/main/stats/derived/build.ts`, each a `DerivedRecipe` (`derived/game.ts`): `{ version, needs, lines, temps, teamBox, boxSource, summedSource, espnKinds, breaks }`. A recipe says only what its sources say differently: which player lines (the temp table `lines`, with each line's team, seconds, counts, plus-minus and starter) and positions, which team box score and how its seconds read, the first season of ESPN's points by kind, and the All-Star dates its schedule lacks. Everything after it is shared: `team_game` (the team beside its opponent, the score from `game`, a forfeit's win from `game.forfeit_winner_id` where the column exists, possessions, PIE's total, rest days, the break), `player_game` with the team's context and the on-court estimates, and the season tables. `NBA_DERIVED` (`game.ts`) is the NBA's SQL as before, at version 2; `WNBA_DERIVED` is `gameWnba.ts` ("The WNBA's recipe" under "Game and season tables"); `COLLEGE_DERIVED` is `gameCollege.ts`, one for the men and the women (T1302.5, `ncaa-data-sources.md`, "Game and season tables, built"). Three optional fields serve the colleges and leave the NBA's and WNBA's SQL byte for byte as it was: `teamBoxKey` (`game_id` where the league has no id of its own beside ESPN's), `boxSourceSql` (a team box from two sources, ESPN's and stats.ncaa.org's, says which per team-game) and `extras` (columns of the recipe's own: stats.ncaa.org's splits and possessions as `ncaa_*` on `player_game`, and on `team_game` for both sides, `src/main/stats/derived/ncaaSplits.ts`). The season tables sum the shared columns and whichever extras the game tables hold (`EXTRA_PLAYER_SUMS`, `EXTRA_TEAM_SUMS`), and the engine reads the extras as components, so a metric over them answers in the leagues that have them. `derived_state('derived')` holds the building recipe's version, `derivedStale(db, league)` compares it with the league's own, and `DERIVED_NEEDS` is every recipe's needs together.

- **`published`** and **`plays`** name the recipes of the published tables and of the tables built from the plays (T1301.7), on the same pattern. A `PublishedRecipe` (`derived/published.ts`) is `{ version, sources, team }`: the league's file where a table's differs (the WNBA's impact file is `src_wnba_impact`; its dashboards are `src_dash_*` as the NBA's), and a team's id in its files as its key in `team` (the 2026 Portland Fire's `-1611661327`). A `PlaysRecipe` (`derived/playsRecipe.ts`) is `{ version, pbp, shots, possessions, gameLineups, officials, side, unlocated, espnThree, espnFoulNames }`: the league's files, a source's team id as the game's side, the condition under which a shot has no location, ESPN's three-point rule over its raw coordinates, and ESPN's foul spellings against the shared ones. The tables, their columns and every builder's SQL are one for every league, so a table not published for a league (tracking, hustle, play types, matchups, the injury report for the WNBA) is built empty. `NBA_PUBLISHED` and `NBA_PLAYS` give the NBA's SQL as before (versions 12 and 7); `playsStale(db, league)` and `publishedStale(db, league)` compare the file's version with the league's own recipe. Where the league's feed carries no players on its rows, the splits' period starters and the assist fallback read the lineup file's ten at the same action instead (a fact of the columns, not of the league).
- **Late sources of identity.** `IDENTITY_LATE` (`src/main/stats/identityLate.ts`) names, per identity recipe, sources of a later tier it reads when they are there: the WNBA's play by play, for a game's overtimes where the core tier leaves them unknown. A refresh that writes one marks identity stale and builds identity and the game tables again at its end, before the published tables and the plays.

**A league before its tables** (the college leagues at T1302.2; from T1302.5 they build `identity` and `derived`, from T1302.6 `published` and `plays` too, the play by play's own tables from T1302.7, and `models` from T1302.8): `builds` lacks the step, and its recipe name and `models` are `null`. With `derived` built and a later step not, the service answers the reads of that step's tables with `notBuiltYet(league, step)` through `offlineStats` (the shots, assists, game flow, on-court units, with-or-without and officials' careers for `plays`; the matchups, lineups, profile, games out and coaches for `published`), and the standings read ESPN's file where the league has no other (`readEspnStandings`). They are read only through accessors that throw on null (`recipeOf(league, kind)` behind `identityRecipe`, `derivedRecipe`, `publishedRecipe` and `playsRecipe`, and `modelsOf`), and a refresh or a read reaches one only for a step `builds` lists: a read of a league whose `derived` is not built answers `notBuilt` (`openStatsService`), the officials reads and the source switch check `builds` before naming a plays or published recipe, and the renderer's Elo view and standings note read `models` as possibly null. `tests/main/stats/collegeLeagues.test.ts` makes every screen's read on both college leagues, off and turned on with an empty file, and none reaches an accessor. The part that builds a league's tables names its recipe and adds its step together.

A later part that needs a league difference in its own builder adds a field to the registry, or a recipe of its own on the same pattern (a name in the entry, a table of recipes beside the builder), and reads it from the league it is handed. No builder tests a league's id.

- **The engine.** `CompileContext.league` is required. The engine reads the league's first season (the lowest season a query may ask), game types (`unknown game type` names the league's list), per-minute modes (`per40` in the NBA is refused, and the reverse), the minimums' base (`Compiled.fullSeason`) and minutes scale, and labels every note and reason with `league.seasonLabel`. A query naming no season type reads the league's default scope (`defaultType`: the regular season, or every counted game in the college leagues, D45). Two college rules, each switched by the league's entry and absent from the NBA's and WNBA's SQL (T1302.5): `divisionIOnly` keeps a board's rows, its ranks, percentiles and league sums, and the scope's average team games to the season's Division I teams unless the query names its players or teams (D40); and a `share` games rule (D43) qualifies a player's per-game leaders (the categories its `perGame` lists: the colleges' add three-pointers made, which `metricIn` gives `qualifyBy: 'games'` there) on their own team's games in scope (`ownGamesCte`: a team's games with a box score, the team with more games for a player of two teams in one season, the seasons added across seasons, by opponent, month or game where the row is grouped so), not the scope's average. `noDataResult(query, ctx)` is its answer for a league with no data: the query is still checked, and every column reads `noData`.
- **The reads.** Reads that label a season or count a game's seconds take the league as their last argument (`readGameFlow`, `readShotChart`, `readAssistNetwork`, `readGameMatchups`, `readOnCourtUnits`, `readWithOrWithout`, `readOfficialsSeason`, `readOfficialCareer`).
- **IPC.** Every `window.api.stats` call names its league first (`api.stats.query('nba', query)`); the handlers check it with `leagueOf` and send it to that league's worker, or to `offlineStats(league, reason)` (`src/main/stats/offline.ts`) when it has none: the answers of a league that is off with no file (`League.noData`), or, with no reason, of one whose worker did not start. Either way `data()` lists the league's releases, none loaded. `stats:changed` carries the league whose data changed.
- **The renderer.** `src/renderer/src/lib/stats/league.ts` holds the league on screen, in that one place. `useLeague()` reads it (a component re-renders when it changes), the hooks in `useStats.ts` pass its id on every call and key every read on it, and `seasonLabel`, `perMinuteModes`, the season-type control and the trends' first season read it. The league menu beside the mark calls `setLeague`, which remembers the league across launches in the renderer's storage (`metis.league`, beside the theme); the app opens on it, `DEFAULT_LEAGUE` (the NBA) when none is saved. `App` builds the shell again for each league, and each league's session (scope, subjects, tabs, boards) is kept above it in `lib/stats/session.ts`; `stats-screens.md`, "League menu", has the rule. Whether a league is off, loaded without tables, or ready is read from `api.leagues.downloads()` through one hook, `useLeagueDownloads` (`lib/stats/downloads.ts`), with `leagueHolds`; the reason a screen shows is the league's status (`noData` or `notBuilt`).

### Which leagues download

The user chooses (D35), and the choice is one row per league in `metis.db`: `league_settings (league, 'download', 'on' | 'off')`. The main process reads it through one helper, **`leagueDownloads(db, dataDir)`** (`src/main/stats/leagueDownloads.ts`), and the renderer through one IPC call, **`api.leagues.downloads()`** (`leagues:downloads`). Each league's answer (`LeagueDownload`): `on`, `hasFile` (its stats file, or the NBA's former `stats.duckdb`, is in the data folder), `fileBytes`, `hasData` (on, or a file kept from before) and `roomNeeded` (its first load's free space, `roomNeeded(league, bytes)`); with them `decided` and the data folder's `freeBytes`. `hasData` is what the registry's constant used to say, now read from the setting and the file.

- **An existing profile** (no choice saved, a stats file present): a league is on when its file is there and off otherwise, written down on the first read. So a profile from before keeps the NBA and downloads nothing for the WNBA until the user turns it on.
- **A clean profile** (no choice, no file) is undecided: no worker starts and nothing is fetched until the first run's question is answered (`FirstRunLeagues`, mounted in the shell). It offers each league with its measured `size` and its free-space check, the NBA ticked, and refuses a choice whose first loads together need more room than is free.
- **Changing it:** `api.leagues.setDownloads({ wnba: true })`. A league turned on gets a worker and a refresh. A league turned off has its worker closed, which interrupts a running refresh, and opened again when its file is read, which no refresh touches from then on (the six-hourly refresh and a resume skip it). Deleting the file is its own call, `api.leagues.deleteFile(league)`, refused while the league is on, and confirmed in the Data panel; it closes the worker and removes the file and its log.
- **The Data panel** lists every league whichever is on screen, with each one's state, files, disk, pause and resume, on and off, and delete (`stats-screens.md`).

`createLeagueControl` (`src/main/stats/leagueControl.ts`) owns the workers and is what `AppContext.leagues` is: `reads(league)` answers a league's reads, `open()` at launch, `refreshAll()` every six hours.

### A file per league, and the rename

Each league has its own file in the data folder, `<userData>/stats-<league>.duckdb` (`statsFilePath`). Before DuckDB opens anything, a worker whose league has a `formerStatsFile` runs `adoptFormerStatsFile` (`src/main/stats/files.ts`): when `stats.duckdb` exists and `stats-nba.duckdb` does not, it renames `stats.duckdb.wal` (when there is one) and then `stats.duckdb`, and logs `stats: renamed stats.duckdb to stats-nba.duckdb`. Nothing is downloaded and nothing rebuilt: the file is the same file. When both exist, the old one is left untouched and the fact is logged. A failed rename stops that league's worker rather than open an empty file, which would start a full download. The installer's data folder (`%APPDATA%\Metis`, kept on uninstall and by updates, D32) is the same `userData`, so the packaged app renames on its first start as the development profile does; neither `electron-builder.yml` nor `build/installer.nsh` names the stats file. `--stats-self-test` opens the NBA's file in a throwaway folder. The scripts open `stats-<league>.duckdb` in the folder they are given, the NBA's unless an argument says `--league=<id>` (`scripts/lib/stats-worker.mjs`).

### The links file and its worker (D47, Plan T1304.2)

The links between a player's college and professional careers (D46) and the paired leagues' season lines (D48) live in one more file in the data folder, `links.duckdb` (`LINKS_FILE`).

- **The name.** It is not `stats-*.duckdb`, which is one league's file, so the per-league size, deletion and adoption of `League.statsFile` never touch it.
- **One worker per file (CLAUDE.md rule 3).** The links file has a worker of its own, `out/main/linksWorker.js` (`src/main/stats/links/`). Only a league's worker opens that league's file, and only the links worker opens `links.duckdb`; nothing attaches one worker's file in another. Its writes run in turn, and each read gets its own connection.
- **When it starts.** Only when there is something to do (`links/control.ts`): a league of a pair has refreshed, or a read asks for such a league (its Data panel, a player's other career).
- **The pairs** are in the league registry, `LEAGUE_PAIRS` in `src/shared/leagues.ts`. Each pair names its college and professional league, how far the professional season labels run ahead (the NBA's draft and seasons by one), the first season of each side's lines, and the tables its paired files read. Code reads the pairs and never names a league.

**The step after a league's refresh**, in the main process, one league at a time:

1. **The paired files** (`PAIRED_SOURCES_BY_LEAGUE` in `sources.ts`): ESPN's player season stats of the other league from its first linkable season, and, for a college league, the professional draft table. They go through the same plan, etags, sealing and `source_state` as a league's files (`refreshStats` with `paired: true`, which builds nothing from them), into tables `paired_<league>_<table>` in the links file. Every column is kept as published.
2. **The league's side.** Its worker writes its side as Parquet into the links worker's hand-over folder (`stats-tmp/links/handover`, named by league and refresh) on a read connection (`links/side.ts`). A professional side is its players with ESPN ids, birth dates and colleges, plus its draft lines; a college side is its players with their ESPN teams.
3. **Metis's own lines.** For each league of the pair whose file is there, its worker writes the `player_season` rows of the linked players, every column, with their `team` rows. They are kept as `kept_<league>_season` and `kept_<league>_team`, which is what a league removed later still shows.

**How the links are built.** The links worker loads each hand-over in one transaction, together with the pair's links (`player_link`, built from scratch by `matchSql` in `links/sql.ts`, D46's matcher ported from the research's queries). A failed or interrupted hand-over therefore leaves the side and the links as they were. The hand-over files are removed once loaded, and on start-up the worker empties its temp folder, so a file a crash left behind is never read.

Each side is kept until that league hands over again, so a league's deletion keeps what it last gave. Where a side has never been handed over, its paired files stand in for it: ESPN's season stats give the ids, names, teams and seasons, and the draft gives the draftees. With one league alone, the links by the id and by name and college are made; name and birth date needs both files.

**When the step fails**, the league's refresh is not failed (it has already ended): the error is logged, recorded as `links:<league>` in the links file's `sync_log`, and shown on the paired files in that league's Data panel until the next refresh tries again.

**The read.** `stats.otherCareer(league, player)` (IPC `stats:other-career`) returns:

- the other league;
- the link and its method;
- the draft line;
- the season rows with their source named: Metis's own lines where they are kept, otherwise ESPN's totals of the paired download, labelled "regular season" for a professional league and "every game" for a college one;
- or the reason there is none: no link, drafted from abroad, or college before the window.

Measured in `player-links.md`, "The link as built".

### Coverage per league

A metric's `firstSeason`, `missingSeasons` and `unavailable` are its coverage in every league whose entry has `metricsByDefault` (the NBA). Any other league is named in the metric's `leagues`:

```ts
leagues: {
  wnba: { firstSeason: 2008 }, // plus-minus, from 2008
  // wnba: { firstSeason: 1997, missingSeasons: [2019] },
  // wnba: null,               // the league does not have it
}
```

`coverageIn(def, league)` gives a metric's coverage in a league, or null where it has none; `metricIn(def, league)` gives the metric as the league reads it, its coverage fields replaced, unavailable with `Not recorded for the WNBA.` where it has none, and the very same object in a league that takes its own fields. The engine resolves every metric through `metricIn` on validation, and `catalogueInfo(league)` sends the renderer each league's catalogue resolved the same way, so a screen reads `firstSeason` and `unavailable` as it always has.

**The WNBA's coverage** (T1301.6) is stated on every metric's `leagues.wnba`, from rules in one place, `src/shared/stats/catalogue/wnba.ts` (`wnbaCoverage`), applied over the catalogue in `catalogue/index.ts` to every metric that states nothing itself, so a metric added later states it too: box-score metrics from 1997; a metric reading plus-minus from 2008, who started (`starts`, `starter_pts`, `bench_pts`, `starts_known`) from 2002, ESPN's points by kind from 2023; tracking, hustle, play types and matchups "Not published for the WNBA: no release holds …", games out "Not published for the WNBA: it has no official injury report …"; team pace per 40 "The WNBA's pace is per 40 minutes already: see Pace.".

**Not built yet.** A metric's table is one of the refresh's steps (`tablesOf`: a model's `models`, a published table's `published`, a built table's `plays`, else `derived`). Where the league's `builds` lacks that step, `metricIn` reads the metric as "Not built for the WNBA yet: its published season stats come in a later version." (`notBuiltYet`, the one place the reason is written), unless its coverage gives a reason of its own; a split of each game reads the same for the plays (`splitGap`). A part that builds a step adds it to the league's `builds`, and the reason lifts with nothing else changed.

**The game length in a formula.** A metric marked `gameLength` holds the game's length in the catalogue's 48 minutes (`CATALOGUE_GAME_MINUTES`): `48` and `2880` (seconds) in its formula, `48` in its label, short label and description. `metricIn` writes them as the league's in a league of another length: Pace is `40 * {poss_sym} / …` and "per 40 minutes" in the WNBA, on-court pace `2400 * …`, WS/48 "Win Shares per 40 minutes" and "WS/40" (the metric's id stays `ws_48`). In the NBA the metric is the very object as written, so its SQL is unchanged. Marked: `team_pace`, `onc_pace`, `ws_48` and the dashboards' two pace metrics. Rates per minute need no mark: per 40 is a mode of the league's (`League.perMinute`).

**The league's own words** (T1301.9). The catalogue is written for the NBA ("as the NBA counts them", "Offensive rating (NBA)", "The NBA's box scores from 1996-97"). A league's `catalogueWords` lists how those words read in it, as pairs replaced in one pass, longest first, each as whole words (`catalogueWordsIn` in `coverage.ts`): the WNBA's sources ("The WNBA's game logs from 1997, its box scores in 2026"), the notes on the NBA's seasons rewritten or left out, a phrase mapped to itself to keep it ("FiveThirtyEight's NBA Elo"), and last every remaining "NBA" as "WNBA", since its league dashboards, play by play and shot charts are the league's own feed. `metricIn` applies them to the label, short label, description and sources of a metric the league has; one it lacks keeps its words beside its reason, and a metric's own `words` for the league (T1301.8's playoff odds) still win. The NBA's list is empty, so its catalogue is the very objects as written. The screens' own lines that name a source are written with `{league}` and read the league on screen (`inLeague` in `lib/stats/league.ts`, `stats-screens.md`).

**What a screen offers.** A metric a league does not have (`unavailable` after `metricIn`) is never offered as a choice: the leaderboards' column picker, family presets and defaults, Explore's presets and Compare's default rows leave it out, and a dashboard tab whose every metric is unavailable is not shown (`shownTabs` in `lib/stats/dashboard.ts`). The Glossary lists every metric with its reason. The same rule holds in the NBA, where DARKO, no longer published, is the one metric it removes.

## Engine

- One worker thread per league (`out/main/statsWorker.js`, `src/main/stats/worker.ts`) owns that league's file. The main process talks to it through `StatsClient` (`src/main/stats/client.ts`): `refresh`, `selfTest`, `status`, `data`, `pause`, `resume`, `close`; the engine's `query`, `catalogue` and `seasons`; and the reads beside the engine (below): `player`, `games`, `game`, `standings`, `matchups`, `gameMatchups`, `officialsSeason`, `officialCareer`, `onCourtUnits`, `withOrWithout`, `lineups`, `profile`, `availability`, `coaches`, `shots`, `assists`, `gameFlow`. Scripts also use `read`, which runs one SQL statement; the app does not expose it.
- Writes run one after another. Reads run at once, each on its own connection, so a screen never waits behind a refresh.
- DuckDB `@duckdb/node-api` 1.5.6. Parquet, JSON and ICU are built in, and no extension is ever downloaded.
- Settings: `memory_limit` 1 GB, 2 threads, `preserve_insertion_order` off, spill files in `<userData>/stats-tmp/<league>/duckdb`.

**Why 1 GB.** The template's 512 MB failed during the first full load: a checkpoint could not pin a block, and DuckDB invalidated the database. A checkpoint pins buffers per column, and these files are far wider than the template's. Reopening the file recovers it, with nothing lost, and the load carries on. 768 MB passed a whole load, so 1 GB leaves room. If it ever happens, the refresh stops, the status reads as stats unavailable, and the next launch recovers.

## Source tables

Each file family in `src/main/stats/sources.ts` loads into one table, named `src_espn_*`, `src_nba_*`, `src_dash_*` (the league dashboards), `src_xwalk_*` (the crosswalks) or by what it holds (`src_team_aliases`).

Every column is kept as published and typed, zeros included. When a later season adds a column, it is added to the table. When a column's type changes between seasons, it is widened (two integer types to `BIGINT`, other numbers to `DOUBLE`, anything else to `VARCHAR`), and the step's message says so.

Three columns are standard:

| Column        | Holds                                                                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `season`      | The file's own value as an `INTEGER`, or the label in the file's name when it has none. It is never overwritten: see the trap in the data reference. |
| `file_season` | The label in the file's name, on season files. It is what a reload replaces.                                                                         |
| `source_file` | The file's stem, on tables that hold several files of a season (play types, hustle, matchups).                                                       |

Season types and team codes stay as published here. They are mapped in the `game` and `team` tables (D27).

## Identity

Built by `src/main/stats/identity.ts`, logged as `stats:identity`, as soon as the core tier has loaded and whenever it changes after that. A new `IDENTITY_VERSION` rebuilds it with nothing downloaded.

| Table        | One row per        | Holds                                                                                                                                                             |
| ------------ | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `game`       | game of the league | `game_id` (the NBA's id, or `espn:<id>` before 1996-97), `nba_game_id`, `espn_game_id`, `season`, `game_type`, `game_date`, teams on NBA ids, the score, `played` |
| `team`       | team in a season   | NBA `team_id`, `espn_team_id`, `code`, `name`, `conference`, `division`                                                                                           |
| `player_ids` | ESPN id            | `player_id`, and the `method` that found it                                                                                                                       |
| `player`     | person             | `player_id`, `name`, `espn_athlete_id`, `method`, `first_season`, `last_season`                                                                                   |

- **Game types** (D12): `regular`, `play-in`, `playoffs`, `cup-final`, `all-star`, `preseason`. From 1996-97 the prefix of the NBA's game id decides. Before it, ESPN's season type, with a game against a touring team counted as `preseason`.
- **What is a game:** the NBA's schedule from 1996-97, ESPN's before. ESPN's rows for postponed games are left out. `played` is false for a game not played, including the one cancelled in 2013.
- **Linking the sources:** the crosswalk, then the same teams within a day.
- **Teams:** `nba_team_aliases` maps ESPN's ids by season, so one NBA id follows a franchise across a move, and ESPN's id 3 is Charlotte through 2001-02 and New Orleans after it.
- **Players**, first hit wins (D28):
  1. the crosswalk;
  2. the same box-score lines in the same games, with at least two lines that are not all zeros and a clear winner;
  3. the same name in the same season, when only one player has it.

  Anyone left gets the negative of their ESPN id: 200 players, of whom one has a line from 1996-97 on.

- **Names:** the NBA's latest spelling from its box scores, else ESPN's. The box scores split a name into first and family, which gets a few wrong (`Ming Yao`, `Nene Hilario`). The rosters have those right but garble others (`Ha Ha` for Seung-Jin Ha), so a roster's name wins only when it repeats no word and every word is in the box score's. That changes four names of 2,913.

- **Reading ESPN's box scores:** add `season = file_season`, or the games of 1998-99 count twice.
- **Reading team totals:** the NBA's box score, or ESPN's players summed before 1996-97. Never ESPN's team rebound and turnover columns.

That is the NBA's recipe. Each league builds these tables with the recipe its registry entry names ("Leagues", "How each league's tables are built").

### The WNBA's recipe (Plan T1301.5)

`src/main/stats/identityWnba.ts`, from the traps measured in [wnba-data-sources.md](wnba-data-sources.md). The same four tables and columns; `nba_game_id` holds the league's own id (`1022600001`), the name kept so later builders read it unchanged. Its checks per season are in [wnba-agreement.md](wnba-agreement.md).

- **What is a game:** the league's schedule, with the two games it lacks (2007 and 2009) taken from the game logs, whose lines for them are players only: the side whose matchup reads `vs.` is at home and the score is the players' points summed (`source` `game logs`). The type is the id's third digit, as for the NBA: `2` regular season, `4` playoffs; no preseason or play-in is published.
- **ESPN's games alone,** both filed by ESPN as regular season and linked by the crosswalk to nothing: the **All-Star Game**, whose two sides are not league teams that season (team ids NULL), and the **Commissioner's Cup final** (`cup-final`), by ESPN's headline from 2022 and by its date in 2021 (`CUP_FINAL_DATES`), when ESPN filed it under the group games' headline. Game ids `espn:<id>` (D28). The Cup's group games are ordinary regular-season games.
- **Linking ESPN:** the crosswalk from 2002, then the same teams within a day, each ESPN row used once; 7,030 of 7,051 games have both ids. ESPN's postponed and cancelled rows link to nothing. ESPN's 2002 Portland home games carry ESPN's team id 12, not Portland's 132052; the crosswalk links them.
- **The 2018 forfeit** (Las Vegas at Washington, 0-0, ESPN `STATUS_FORFEIT`) is `played`: it counts in the standings with no box score. `forfeit_winner_id` names the side ESPN's standings give one win more than its scored games (Washington). A 0-0 row ESPN does not mark a forfeit would be not played.
- **Columns beyond the NBA's:** `neutral` (ESPN's `neutral_site`, NULL where the game has no ESPN row), `periods` (regulation periods by season from the registry: 2 halves to 2005, 4 quarters from 2006), `overtimes` (from the game logs' team minutes, 200 plus 25 an overtime, when they are 200 or more; else from ESPN's last period on a final row; NULL before 2002, when the game logs' team minutes are 0 and ESPN's rows are not final), `forfeit_winner_id`.
- **Teams:** one row per team the schedule or game logs list in a season, on the league's team id, which follows a franchise across a move (Utah, San Antonio, Las Vegas; Detroit, Tulsa, Dallas; Orlando, Connecticut). The code and name are the season's latest in the league's schedule; ESPN's id is the alias table's for that season; the conference is the groups table's; `division` is NULL, as the WNBA has none. **The 2026 Portland Fire** share the 2000-2002 club's id in both sources: an id the alias table gives a second span of seasons after a gap is a new club, and its rows take the negative of the id (D28's way: one key per club; `-1611661327`). A source row reaches it as `abs(team_id)` in its season.
- **Players:** the league's id from the game logs (every season to 2025, 202 of 2026's games) and the 2026 box scores (every player listed, as the NBA's box scores list them). ESPN's ids through the shared matching: the crosswalk (an ESPN id the crosswalk puts on two league ids takes the one it gives in most seasons), the same box-score lines, the same name in the season over the lines and the league's rosters; anyone left gets the negative of their ESPN id. The players of 1997 to 2001 have the league's id alone (`method` `wnba only`). Names are the league's latest, as published, accents kept (`Marie Gülich`). `player` adds the roster's latest `position`, `height`, `weight`, `birth_date` and `school`, the position falling back to ESPN's athlete file; NULL where neither has one.

## Game and season tables

Built by `src/main/stats/derived/`, logged as `stats:derived`, right after identity and whenever it runs. A new `DERIVED_VERSION` rebuilds them with nothing downloaded. Each replaces the old table in one statement, so a screen reads the old rows or the new ones. The build takes 14 seconds on the full database.

| Table           | One row per                                     | Holds                                                                                                                 |
| --------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `team_game`     | team in a game played                           | Its box score beside the opponent's (`opp_`), the score, estimated possessions, ESPN's points by kind, game context   |
| `player_game`   | player in a game they appeared in               | Their box score, whether they started, their position group, the team's and opponent's totals, the game context       |
| `team_season`   | team, season and game type                      | `team_game` summed                                                                                                    |
| `player_season` | player, season, game type and team, and no team | `player_game` summed. The row with no team is the whole season: a traded player's is never the sum read beside others |

No rate is stored. Every column is a count or a sum over the same games, divided when read, so any date range or group of games is exact.

- **Which box score:** the NBA's wherever it has the game, which is everything counted from 1996-97. ESPN's before that, and for the 17 All-Star games it has. Preseason games have no box score anywhere, so they are in `team_game` with a score and `box_games` 0, and in `player_game` not at all.
- **Team totals:** the NBA's team box score, which equals its players on every count (one game aside). Before 1996-97 ESPN's players summed, never ESPN's team columns. Those totals have only player-charged turnovers: team turnovers are not in this box score.
- **A game with no box score** (26 team-games before 1996-97) still counts toward a record: `games` and `box_games` differ, and points for and against come from the schedule.
- **Appearing:** the NBA's non-empty `minutes`, or an ESPN line with minutes and not marked as not played. `seconds` reads `6:34`, `240:00` and the bare `26` on 88 old lines.
- **Started:** the NBA's position from 2017-18, when it lists one for starters only; ESPN's flag before it. A team-game without exactly five flagged reads NULL: unknown, not all bench. `starts_known` counts the team-games where it is known, so bench points can be per game of those.
- **Position group** (`G`, `F`, `C`): the NBA's roster that season, then what its box scores list most, then ESPN's. A hybrid takes the first listed: `G-F` is a guard, `F-C` a forward, `C-F` a center.
- **Possessions are estimates:** `poss` and `opp_poss` are `FGA + 0.44 FTA - OREB + TOV` for each side, `poss_sym` their mean, `poss_bref` the rebound-adjusted form. See reference section 5.
- **Estimated on-court totals:** `x_*_den` and `on_poss` are what a player's team did while they played, guessed game by game from their share of its minutes (`5 × seconds / team seconds`), for Basketball-Reference's AST%, ORB%, DRB%, TRB%, STL%, BLK% and USG%.
- **`rest_days`:** full days off since the team's last game that season, 0 on a back-to-back, NULL for its first. Preseason games are counted apart.
- **`after_break`:** against the date of the All-Star Game that was played, or one still to come this season. Before 1996-97 the schedule has none, so those three dates are in the code, each checked against the gap in that February's games. 1998-99's was cancelled, so that season reads NULL.
- **Plus-minus** is the NBA's, from 1996-97. ESPN's column is zero before then, and is not read.

That is the NBA's recipe. Each league builds these tables with the recipe its registry entry names (`League.derived`, "How each league's tables are built"); the season tables are one for every league.

### The WNBA's recipe (Plan T1301.6)

`src/main/stats/derived/gameWnba.ts`, from the traps in [wnba-data-sources.md](wnba-data-sources.md). The same four tables and columns; a real refresh builds them in about 3 seconds (14,058 team-games, 136,532 player lines, 622 team-seasons, 15,164 player-seasons). Its checks per season are in [wnba-agreement.md](wnba-agreement.md), "Game and season tables".

- **Which box score:** the player lines are the league's game logs (every player-game to 2025, 202 of 2026's games) and its 2026 box scores, which hold every 2026 game and agree with the game logs on every line both have: a game the box scores hold reads from them, any other from the game logs (`source` `wnba`). The team lines are the game logs' team rows, every team-game from 1997; a count where the team row falls short of its players reads the players' sum, turnovers adding the team's own from the play by play (most games of 1997, 2000 and 2003, whose rows carry almost no turnovers; one game each in 1999, 2006 and 2008), points staying the row's, which equals the score (version 2, T1301.7). ESPN's lines are read only where the league has none: the Commissioner's Cup finals (2021 on), ESPN's alone (`source` `espn`), with the team summed from them. ESPN's counts are read from 2003: its 2002 lines are all zeros (`ESPN_COUNTS_FROM`).
- **Keys:** a source row's team is the game's side whose key it is, `abs(team_id)`, so the 2026 Portland Fire's lines are on `-1611661327` (T1301.5).
- **The All-Star Game** has no league teams (its sides are NULL in `game`), so it has no team or player lines, as the NBA's games without two teams have none.
- **The 2018 forfeit** is a win for the side `game.forfeit_winner_id` names and a loss for the other, `games` 1, `box_games` 0, points 0-0: the game logs' two team rows of zeros are not read as a box score (a team row with no field-goal attempt and no point is none).
- **Appearing:** every game-log row (a few at 0 minutes, which still count), a box-score line with `minutes`. **Seconds:** the game logs' whole minutes times 60; the 2026 box scores' `mm:ss` to the second. A team's seconds are its minutes from 2005 (200 in regulation, 225 with an overtime); before, the game logs print 0 (12 in 2004), so they are the regulation and overtimes `game` knows (most games from 2002), else the players' whole minutes summed (1997 to 2001).
- **Started:** ESPN's flags from 2002, its zeros of 2002 included, and the 2026 box scores' positions, listed for the five starters only; a team-game without exactly five flagged reads unknown, as for the NBA: none before 2002, 75 to 95 % of team-games in 2002 to 2005 (ESPN's 2003 box scores cover 195 of 256 games, and a starter ESPN has under another id leaves four), 96.9 to 100 % from 2006.
- **Plus-minus** from 2008: the game logs' column is null on every line before but 0 to 62 a season, so it is not read then (`PLUS_MINUS_FROM`).
- **Position group:** the league's roster that season (`G`, `F`, `C`, `G-F`, `F-C`, `F-G`, `C-F`, the first listed the group), then ESPN's.
- **ESPN's points by kind** from 2023, when its team box score first has them. **After the break:** the All-Star Game that season (none in 2008, 2012, 2016 and 2020).

## Plays, shots and possessions

Built by `src/main/stats/derived/playBuilders.ts` from the SQL in `plays.ts` and `events.ts`, logged as `stats:plays`, once at the end of a refresh, season by season (below). They are keyed to `game` and `team`, so season types, team codes and the All-Star games ESPN files as regular season come from there (D27). Each source has its own table or view and they are never merged (data policy 5). How well they agree with the box scores is in [nba-plays-agreement.md](nba-plays-agreement.md), and the traps behind each rule in [nba-data-sources.md](nba-data-sources.md), "Plays".

| Object       | Kind  | One row per                                  | Holds                                                                                    |
| ------------ | ----- | -------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `play_nba`   | table | row of the NBA's play by play, 1996-97 on    | The play keyed to the game, its clock, the score after, who acted and the counting flags |
| `play_espn`  | view  | row of ESPN's play by play, 2001-02 on       | The same columns, worked out on read from `src_espn_pbp` (Plan T907)                     |
| `plays`      | view  | row of either, with `source` (`nba`, `espn`) | Both, plus `elapsed` and the score before                                                |
| `shot_nba`   | view  | shot in the NBA's shot chart                 | Made, value, distance and the NBA's coordinates (tenths of a foot from the basket)       |
| `shot_espn`  | view  | shot or free throw in ESPN's file            | Made, the value of a make, the second athlete and ESPN's coordinates                     |
| `possession` | view  | possession in SportsDataverse's derived file | Offense, defense, the plays it spans, points, its counts and the ten players on court    |

**What later work can rely on.** Sum flags; do not parse text.

- **Keys:** `game_id` with `seq`, the order within the game and the source's own row key (the NBA's `order_index`, ESPN's `game_play_number`). `possession.start_seq` and `end_seq` are `seq` in `play_nba`.
- **Time:** `period`, `clock` (seconds left in it) and, in `plays`, `elapsed` (seconds since the tip-off: 720 a quarter, 300 an overtime).
- **Score:** `home_after`, `away_after` stored; `home_before`, `away_before` in `plays`, the score after less the play's points.
- **Who:** `team_id` and `player_id` act; `opponent_id` is the other side, `home` whether `team_id` is at home. A row with a team and no player is the team's own (a team rebound, a shot-clock turnover).
- **Flags** (`UTINYINT`, 0 or 1, `pts` 0 to 3): `fga`, `fgm`, `fg3a`, `fg3m`, `fta`, `ftm`, `pts`, `oreb`, `dreb`, `tov`, `pf` belong to the actor; `ast` to `assist_id`, of the same team; `stl` and `blk` to `steal_id` and `block_id`, of `opponent_id`. They sit on the turnover, the make or the miss they belong to, in both sources.
- **A box-score line** is those sums, with rebounds and turnovers of rows that have a player: the box score leaves team rebounds and team turnovers out. That is how `scripts/check-plays.mjs` rebuilds it.
- **`kind`** is one set for both sources: `field_goal`, `heave`, `free_throw`, `rebound`, `turnover`, `foul`, `steal`, `block`, `violation`, `jump_ball`, `substitution`, `timeout`, `period`, `replay`, `ejection`, `other`. `action` and `subtype` keep the source's own type text, for turnover and foul types.
- **`possession`** is the NBA's possession number in `play_nba`; ESPN has none.
- **Default source: the NBA's** (`DEFAULT_PLAY_SOURCE`). It starts five seasons earlier, carries possessions and the players on court, is the feed behind the box scores the app trusts, and matches them better: see the agreement report. A metric reads ESPN's only for what the NBA's lacks.
- **ESPN's plays are worked out on read, for checks, not screens** (Plan T907). `play_espn` is a view over `src_espn_pbp`, the same SELECT a season's build used to store, for every season at once; storing it took 243 MB that nothing the app shows reads (fouls drawn read `src_espn_pbp` directly). A filter on `season` reaches the file's own season, so a season counts in about 40 ms and all 14.3 million rows in 0.6 s; working out a season's lines, as `scripts/check-plays.mjs` does, costs about 2.8 s more than reading a stored table (the whole check 89 s instead of 17, the same report). In `plays`, a filter `source = 'nba'` leaves ESPN's side out of the plan. With no ESPN file the view is empty. A database built before holds the old table: the next build drops it and checkpoints before writing, so its space is reused.

**Built season by season.** Each file of the core, events or plays tier that writes rows marks its season in `derived_state` (`plays:<season>`) as it loads, so a refresh cut short still rebuilds it next time. At the end of the refresh the step rebuilds only the marked seasons that have games played: a current-season file never rebuilds a sealed season. Every season is rebuilt when `PLAYS_VERSION` changes (a new database has none), when a table's columns differ from its builder's, or when a file of every season (season 0, the aliases) wrote rows; a full rebuild also deletes seasons no longer played. A season is replaced in one transaction per table, its rows deleted and its new rows inserted, so a reader sees it whole, old or new, never half; a season that fails rolls back and stays marked. DuckDB is asked to checkpoint after each season, so the space of the deleted rows is reused by the next.

**The registry.** `PLAY_BUILDERS` in `playBuilders.ts` is the ordered list of tables built from plays. Each entry names its table, its typed columns, a SELECT of one season's rows and the order the rows are written in (`order`, game first: rows of a game side by side compress 8 to 26 % better and a read of one game skips the others' row groups, Plan T907); the step does the rest (shape, delete, insert, transaction, checkpoint). Plan T902 to T905 add their built tables by appending one line there, never by editing `sync.ts`. The rule for an entry: **per season** (the table has `season`, and one season's rows depend on that season's data only), **one transaction a season**, and **counts, not rates** (rates are divided when read, so seasons can be replaced apart). An entry runs after the ones above it, so it can read their tables.

**Cost, measured** at Plan T901, with only the play tables and before the later builders were added, on a copy of the full load through a real refresh (`scripts/load-report.mjs`): a full rebuild of 33,327,811 rows takes 94 to 276 seconds (the slowest the first, on a file the one-statement build had left) with the file peaking at 5.13 GB from 5.12 GB in steady state, and 5.42 GB the first time; a rebuild of the current season alone writes 154,413 rows in 1.5 seconds with no growth. Peak memory of the refresh process is 2.2 GB for a full rebuild, 0.5 GB for the current season. With every play table of Stage 9, a full rebuild writes 34.9 million rows in 443 seconds, the file peaking at 5.38 GB ([nba-data-sources.md](nba-data-sources.md), "The first full load").

**View or table, measured** on the full Stage 8 load, warm, a season's scan grouped by player or team-game: `play_nba` as a table answers in 10 to 31 ms; as a view it would redo its window functions, about 6 seconds a season. The shots and possessions answer in 15 to 38 ms as views and 4 to 15 ms as tables, and copies would cost about 540 MB and 11 seconds of build, so they stay views. Deeper pre-aggregation is T907's.

### Metrics on a built table (`built`)

The one mechanism for tables built from the plays that the engine reads at both grains (the shot tables first; on/off and the other play-derived tables use the same). A metric names the table in `built`; the table is listed in `GAME_TABLES` (`src/main/stats/derived/gameTables.ts`); the engine needs no other change. It is apart from `published` and `publishedGames`, which are the dataset's season files and their game-grain companion (Plan T906).

**What the table must hold**

- One row per player or team and game, or several, which are added up. Counts only, never a rate: each rate is a numerator and a denominator, both columns, divided by the metric's formula (data policy 3).
- `game_id` (the `game` table's id, as in `player_game` and `team_game`), `season`, `game_type`, and the column named as its `key` in `GAME_TABLES`: `player_id` for a player table, `team_id` for a team table.
- `team_id` on a player table too: the player's team in that game. The season grain needs it for a traded player (below).
- Every column the metrics read, listed in the entry's `components`. A team table holds the opponents' side as `opp_*` columns of its own, since `swapSides` only knows the box-score names.
- Optionally `zero(component)`: the components that read 0, not null, for a row in scope that has no row in the table (a player who took no shot took none from the corner). Leave out what has no honest zero, such as an expectation in a season with no league rate yet: those read null.

It is built season by season by appending a `PlayBuilder` (`table`, typed `columns`, `select(have, season)`) to `PLAY_BUILDERS` (`derived/playBuilders.ts`). It is created empty on every open from its own bootstrap, so a query before the first build reads zeros and nulls, not a missing table. A builder that reads a view (`shot_nba`, `possession`) must read the view's SELECT for its season (`nbaShotsSelect(have, season)`), because the views are created after the builders run.

**How each grain joins.** The engine first takes the box-score rows in scope (`base`: `player_game` or `team_game` at the game grain, `player_season` or `team_season` at the season grain, after every filter and the last N games). Then `builtCte` sums the table per output row, `base LEFT JOIN table`:

| Grain                                                                                              | Join                                                                                                                    | What it gives                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Game (a date range, last N, an opponent, home or road, any split, grouping by anything but season) | `w.key = b.id AND w.game_id = b.game`                                                                                   | Exactly the games in scope. Groups by what the query groups by                                                                                                                         |
| Season (whole seasons, by season or not)                                                           | `w.key = b.id AND w.season = b.season AND w.game_type = b.game_type AND (b.row_team IS NULL OR w.team_id = b.row_team)` | A season and season type. A player's row of no team reads every team they played for; with teams named, each team's row reads its own games, so a traded player is never counted twice |

Both also keep to `w.season IN` the seasons in scope, so DuckDB skips the other seasons' row groups. The sums join back to the box-score sums by row (and by every grouping dimension), so neither multiplies the other.

**Where games, minutes and possessions come from.** A component the table does not hold is read from the box-score sums of the same rows: `games`, `box_games`, `minutes`, `on_poss`, `poss_sym`. So a count's per game divides by the games played in scope (a team's by `box_games` when the metric sets `perGameBy`), per 36 and per 48 by the box score's minutes (a team's divided by five, as for any box-score team metric), and per 100 by the estimated possessions (`on_poss` for players, `poss_sym` for teams). Qualifying (`minSample`, scaled to the team games in scope) and ranks work as for any metric.

**A table that brings its own divisor.** Two ways:

- Name the column after the box-score component it replaces (`minutes`, `on_poss`, `poss_sym`, `games`) and list it in `components`: the engine reads a component from the table whenever the table holds it, so per 36 or per 100 then divides by the table's own. A team's minutes are still divided by five under per 36, so a team table's `minutes` must be all five players' minutes, as the box score's are.
- Or give it its own name (`shots_fga`, `poss_on`) and use it in the formula and as the `sample`, with `totalOnly` or `perGameOnly` on counts the box-score divisors would misread.

**Splits.** A built table counts per game, not per moment of a game, so under `scope.split` (Plan T902) a built metric reads null with "Counted per game, not per moment, so it has no split.", never its whole-game value. A table that wants splits must hold them itself.

**Coverage.** A metric's `firstSeason` (and `missingSeasons`) gives the reason a season outside it reads null ("Recorded from 1996-97."); inside it, the zeros and nulls above. `grainsOf` gives a built metric both grains when every component is in the table or in the box-score tables, and none otherwise. The catalogue test reads such a metric from a worked row of the table's components.

### Play-derived stats (Plan T905)

`play_player_game` and `play_team_game`, built by `derived/playDetail.ts` as the last two builders of `PLAY_BUILDERS`, from `play_nba` of the same season (815,281 and 79,058 rows on the full load, 16.5 and 6 MB). Counts only, a byte a count; times in tenths of a second. The rules are data in `src/shared/stats/playDetail.ts`, shared by the SQL, the read and the screens; how each agrees with the box scores is in [nba-data-sources.md](nba-data-sources.md), "Play-derived stats".

- **A player's row:** turnovers, live (a steal credited) and dead, and by kind (bad pass, lost ball, offensive foul, traveling, shot clock, stepped out, other violations, other), which add up to them; personal fouls and their ten kinds, which add up to them; technicals (defensive three seconds apart); ejections; made twos and threes, assisted and not; and-ones and those converted; two- and three-shot foul trips; defensive goaltending and kicked balls; assists on twos and on threes (the passer's); fouls drawn and shooting fouls drawn, from ESPN's play by play (the only feed that names the fouled player).

The other team's side is on the same row as `opp_*`.
- **Assisted makes** are `play_nba`'s `ast` flag, the one the shot tables (Plan T903) read through the shot file: the two agree on every player-game the shot file has.
- **The flow's rules** (`flowSummary`): the score changes only on a scoring play; a tie is a scoring play that levels the score, not 0-0 at the tip; a lead change puts a side ahead when the other led last, a tie between or not; a run is the points one side scores with none by the other between, any point ending it, a free throw included, across period breaks; a drought is the longest time without a point (or field goal), from the tip, between scores and to the end, on the game clock. The scoring rows are read by `scoringRowsSql`, shared with the game-flow read: the score is the play table's, in order of the total score, then of the row, since the feed lists a few scoring rows out of order (see the traps).
- **Read by the engine** through the `built` field: 162 metrics in the Play by play family (`catalogue/plays.ts`), counts per game, per 36 or per 100 from the box scores' divisors, shares and rates divided on read, flow averages over `flow_games`. Counts read 0 for a row in scope with no row; the flow reads null there. Under a split they read "Counted per game, not per moment, so it has no split."; before 1996-97 "Recorded from 1996-97."; fouls drawn outside 2006-07 to 2016-17 their reason.
- **Two reads beside the engine,** on their own calls (`playReads.ts`): `assists` lists passer and scorer pairs from `play_nba` over the games of a scope, as the shot chart scopes them; `gameFlow` gives one game's scoring plays in order and its `flowSummary`. Each answers in 20 to 25 ms a season, 45 to 51 ms over ten (measured), so neither stores anything.
- **Cost:** the two builders alone rebuild 31 seasons in 33 seconds with no growth of the file; in the real refresh that rebuilt every play table (plays, shots, splits and these) the `stats:plays` step took 507 seconds for 47.6 million rows, the file going from 5.16 to a peak of 5.65 GB and 5.59 GB after, peak memory 2.4 GB. With every Stage 9 table (T904's on-court tables too), a real refresh of a fresh copy of T901's load (`PLAYS_VERSION` 5) took 17.5 minutes, its `stats:plays` step 986 seconds for 49.2 million rows; the file went from 5.16 GB to a peak of 5.73 GB and 5.71 GB after, peak memory 2.3 GB, against D22's 6 GB, an hour and 4 GB.

| Table          | One row per            | Holds                                                                                                                      |
| -------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |

## On court

Built by `src/main/stats/derived/onCourt.ts` (Plan T904) at the end of the `stats:plays` step, a season at a time, each season in one transaction a table: the last two of `PLAY_BUILDERS` (`derived/playBuilders.ts`), after the plays they read, so a season whose files changed rebuilds them with its plays. Both hold counts, never rates (data policy 3), and a missing source or column reads NULL: no lineup file, no players on the floor; no possessions file, no possessions. How well they agree with the box scores and the NBA's lineups is in [nba-data-sources.md](nba-data-sources.md), "On court, per season".

| Table             | One row per                                | Holds                                                                                                   |
| ----------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `unit_game`       | team, game and set of players on the floor | The players (`p1` to `p5`, ascending), `complete` when five are known, seconds, and 15 counts each side |
| `player_on_court` | player and game                            | The team's and the opponent's counts with the player on and off the floor, and the player's own counts  |

**How a play is credited.**

- **Who:** SportsDataverse's lineup of each play (`nba_stats_game_lineups`, through `src_nba_pbp`'s `action_number`), which changes at the play of a substitution. The possessions file's players are the possession's first five only, so a substitute who comes in between free throws is missed: with them, on-court plus-minus equals the box score's on 26 to 40 % of player-games; with the per-play lineups, on 89 to 97 %. A play the lineup file has no row for takes the lineup before it in the period.
- **Free throws** count for the players on the floor at the foul, as the official plus-minus does.
- **Time** is the clock between a play and the one before it in its period (720 seconds a quarter, 300 an overtime), credited to the players on the floor at the play. A possession's own clocks do not chain (each starts at its first play), so they are not used.
- **Possessions** are the possessions file's (those it counts), each credited to the five on the floor at the play that ends it. They are SportsDataverse's count, about 5 % below the NBA's.
- **Counts** follow `play_nba`: rebounds and turnovers are a player's, as in the box score; a steal or a block sits on the other team's play and is credited to the side of the player who made it.
- **Units:** a five-man unit is a row with five distinct players known (`complete`); a lineup with a player missing (0.05 to 0.1 % of possessions) or listed twice still counts for the team and the players known.
- **Off the floor** is the team's line in the game less the player's on-court line, so on plus off equals the team's exactly, and it covers the player's own games only, not games they missed.

**What reads it.**

- **The engine** reads through the On court metrics' field, the same mechanism as the shots ("Metrics on a built table"): joined to the box-score rows in scope by player and game under a filter that splits a season, by season, season type and the row's team over whole seasons, so a traded player's one team reads exactly. The table holds the counts and the on-court minutes; games come from the box scores. Per 36 and per 48 divide by the minutes on the floor and per 100 by the possessions on the floor (), both the table's own, since reads a divisor from the table when the table holds it. Under a split within games (Plan T902) they read "Counted per game, not per moment, so it has no split." No new subject: a player's on/off is a player metric.
- **`onCourtUnits(team, season, scope, size)`:** a team's groups of two to five players in a season and scope (season types, a date range or the team's last games), every group the plays put on the floor, from `unit_game`. A five is a complete unit; a smaller group is any players known together, whatever the rest of the floor. Counted on read, so nothing is stored per pair, triple or four.
- **`withOrWithout(player, teammate, season, scope)`:** the player's team in the games both played for it: both on, the player alone, the teammate alone, neither; with no teammate named, the one they shared the most minutes with, and the list of teammates for a picker.

## The catalogue and the query engine

`src/shared/stats/catalogue/` holds every metric, one file per family: `traditional`, `shooting`, `possessions`, `scoring`, `composite`. Each states the fields of reference section 19.4: entity, kind (recorded, derived, estimated, model), aggregation (a sum or a ratio of sums), unit, sample, direction, sources and first season. Its formula is SQL over component sums (`{fgm} / nullif({fga}, 0)`), so adding a metric needs no engine change. Every formula has a test against a value worked by hand, and the test fails for a metric that has none.

`src/main/stats/engine/` answers a `StatsQuery`: `compile` checks it and writes parameterised SQL, `run` executes it under a five-second timeout on its own connection. Nothing from a query is spliced into SQL.

- **Which table:** `player_season` or `team_season` unless a filter splits a season, then `player_game` or `team_game`. Both give the same numbers. A player's season table is read either as its rows with no team or as those of the teams named, never both, so a trade cannot count twice.
- **Scope:** seasons, game types (default the regular season; All-Star and preseason only when asked), a date range, last N, position group, team, player, one game by its id. Then the game's context: opponent, the opponent's conference or division, month, home or road, before or after the All-Star Game, rest days, starter or bench, win or loss.
- **Last N:** a player's own last N appearances, or their part in their team's last N games, which they may have missed.
- **Split** (`scope.split`, Plan T902): only the moments of each game in the split count. The query reads the game grain, joins `split_player` (or `split_team`) to the game lines by player or team and game, so every game filter, a date range and the last games hold exactly; the last N are the player's own games, then the split within them. Each component maps to its split column (`SPLIT_PLAYER_SQL`, `SPLIT_TEAM_SQL`): the counts, minutes from the seconds, the team's and opponent's counts in the same split for shares, the on-court estimates over the player's share of the team's time in it, and per 100 over the possessions counted from the plays. A metric with a component the split rows lack reads null with "Not counted from the play by play, so it has no split.", and a scope with no season from 1996-97 on "Splits are counted from the play by play, from 1996-97.". Qualifying scales `minSample` by the split's share of the team's time in scope.
- **Transforms:** totals, per game, per 36, per 48, per 100 possessions. A ratio reads the same in each, and a record stays a total. Per 100 uses estimated possessions: a player's are their team's times their share of its minutes. A team's per-game count divides by its games with a box score.
- **Qualifying:** a metric's `minSample` is for 82 games and scales to the team games a row covers, so a short season or a date range qualifies fairly. A row per season reads its own season's games. Teams always qualify. A row grouped by opponent or month needs its share of the season, over the league's `seasonShape` (29 opponents and six months in the NBA, 11 and four in the WNBA, D37).
- **Minimums:** 500 field-goal attempts for field-goal rates, 400 for two-point percentage, 200 three-point attempts, 125 free-throw attempts, 100 turnovers for assist-to-turnover, 1,000 minutes for the rest.
- **Ranks and percentiles:** among qualified rows of the same position group, and of the same group when grouped.
- **Coverage:** a metric with no season in scope reads null, and its column says why ("Recorded from 1996-97."). A query never fails over a gap, and a gap is never a zero. Sorted on such a column with only the qualified asked for, a table still lists its rows, since nothing could qualify.
- **What the open file holds** (`CompileContext.schema`, the fix of a 1.3.0 file opened by a later build): a metric whose component column or table the file does not have yet reads null with "Built at this league's next refresh.", for that metric alone, and the rest of the query answers. See "A file older than the build" below.
- **Grouping:** by season, team, opponent, month or game.
- **The league in the same scope** (Plan T1006): a query with an index or a shrunk rate adds a second aggregate (`leagueCte`, its CTEs prefixed `l_`) over every player or team in the same seasons, season types and games (dates, opponents, home or road, a split, every game filter), whatever narrows the rows (a position, a team, the players asked for, a starter filter, the last N games). It is grouped by the query's season and month, so a row by season reads its own season's league. Each metric that needs it reads its own formula on the league's sums (`lv<i>`), the league's totals divided (data policy 3), never an average of players' rates.
- **League indexes** (`MetricDef.index`, Plan T1006): an entry names the rate it indexes and copies its formula and sample; the engine replaces the value by 100 × rate / league, or 100 × (2 − rate / league) where the rate's own direction is lower (turnover percentage, the opponents' shooting), so above 100 is better and a zero stays finite; a rate with no better side (usage, three-point attempt rate) is not mirrored. They are the League indexes family (`catalogue/indexes.ts`, `leagueIndexes`), 16 for players (TS+, eFG+, FG%+, 2P%+, 3P%+, FT%+, 3PAr+, FTr+, TOV%+, AST%+, ORB%+, DRB%+, TRB%+, STL%+, BLK%+, USG%+) and 21 for teams (both sides of the nine shooting and four-factor rates, and the team's three rebound rates). Left out: ratings and pace, which are already per 100 possessions and have no conventional index, assist-to-turnover (a ratio with no bound), and counts. An index qualifies, ranks and has gaps as its rate does.
- **Shrunk** (`StatsQuery.shrunk`, Plan T1006): each rate (`aggregation: 'ratio'`, not a state) with a measured prior `k` reads (sample × value + k × league) / (sample + k), the league as above; an index is pulled toward 100. The raw value stays in `raw`, the column says `shrunk`, and the notes say what was done and name the rates with no prior. Counts are not shrunk. A shrunk metric ranks every row with a sample (`s > 0`), not only the qualified ones, and a shrunk sort puts those rows first. Not with `percentile`, `zScore` or `vsLeague`. The priors come from `metric_stability` (below), read once and kept by the service until a refresh ends, and passed to the compiler as `CompileContext.priors`.
- **The rank pool of a tab** (`StatsQuery.rankAmong`, the fix of the 1.2.0 college boards): a metric of the query, a leaderboard tab's qualifier (`min`). Each other metric that does not qualify by its own minimum alone (`qualifyBy`, D33, D43) and is not shrunk then ranks among the rows that qualify on it too: its window's pool is `q<i> AND v<i> IS NOT NULL AND q<k>`, `k` the qualifier, the rule a board applies on the client when it holds every row (`rankWithinTab`). The college boards send it (`League.manyRows`); a query without it compiles as before. Measured on NCAA Men 2026-27: a board of ten columns 81 ms with it, 84 without; 40 columns 306 and 265 (`engine-speed.mjs`).
- **Places** (`StatsQuery.places`, Plan T1601.3): `{ ids, standing, orSample }` answers only the rows named, each with `StatsRow.place`: `all`, its place in the whole order the other forms list (qualified for the sort first, the sort, the name), and `standing`, its place among the rows that qualify for `standing` (a metric of the query, or null for every row), or that have a sample of the sorted metric when `orSample`; null when the row itself does not stand. No limit applies, so a row past the 5,000th still has its place. It is the same SQL as a list, with `row_number()` and a filtered running `count(*)` over one window in that order, then `WHERE id IN` the ids (bound, at most 500, each an id). Not with `groupBy`. A leaderboard filtered to favourites asks it for the favourites it did not fetch, so they keep their league rank (`stats-screens.md`, "Favourites"). Measured on the four-league profile: about 65 ms for NCAA Men's 5,059 player rows, the same as the board's own query; `scripts/engine-speed.mjs` unchanged before and after, since no other query's SQL changes (`nbaSqlUnchanged.test.ts`).
- **Filters** (`StatsQuery.filters`, D51): conditions on attributes and metrics, applied after the ranks: see "Attributes and filters".
- **Published metrics:** see below.

### Metrics with no game behind them

Hustle, tracking, play types and the rest are published per season, so they have only the season grain. A metric says so by naming its table in `published`, and its formula reads that table's columns. Each table is listed in `src/main/stats/derived/publishedTables.ts` and built by `derived/published.ts`: the source's rows of totals, keyed on player or team, season and game type, with `games`, `minutes` and `possessions` beside its own columns. They are created empty on every open, so a query before the published tier has arrived reads null instead of failing, and the `stats:published` step fills them once that tier is in. A family adds its table to the list and its metrics to the catalogue, with no engine change, and bumps `PUBLISHED_VERSION`.

A component can also be worked out from the source's columns, as `{off_rating} * {poss}`. That is how a rate the source publishes ready-made is stored: the NBA's dashboards give usage, ratings, PIE and shares as rates without their parts, so each is stored times what it was measured over, minutes or possessions for a rating, and divided back when read. One season reads exactly as published, and seasons or season types added together are weighted by minutes or possessions. A player or team with 0 minutes or possessions published reads no value there, where the NBA prints 0.

The NBA's dashboards (Plan T702) are nine tables: `pub_player_advanced`, `pub_player_misc`, `pub_player_scoring`, `pub_player_usage`, `pub_player_defense`, `pub_team_advanced`, `pub_team_four_factors`, `pub_team_misc` and `pub_team_scoring`. Their metrics are in `src/shared/stats/catalogue/dashboards.ts`, with ids starting `nba_`, `team_nba_` and `opp_nba_` beside the formula versions (D14). On the full database they build 108,582 rows in 1.1 seconds. A season's leaderboard with ten box-score columns and six published ones from five of these tables answers in 141 ms (median of seven, 150 at worst), against 114 without them; every season from 1996-97 at once, 226 ms.

**A table that adds rows** (Plan T1206). The engine's rows start from the box scores, and a player listed Out of every game of a season or a playoff run has no line there. So the availability table is marked `addsRows` in `publishedTables.ts`, the one place that says it, and holds three columns about who each row is for (`ADDED_ROW_COLUMNS`): `row_team_id`, the team on the player's last counted report that season and type; `row_position`, their position group on the NBA's roster that season; `row_name`, the name the report prints, family name first, turned round ("Butler III, Jimmy" reads "Jimmy Butler III"). Each is NULL where the source has none, and the bootstrap adds them to a table built before. When a query reads a metric of such a table with an answer, at the season grain and not for the stability measure, `addedCte` in `engine/compile.ts` takes the table's players with any of the counts the query reads above 0, in the seasons and season types in scope, who have no row in `player_season` (the whole season, no team) for that season and type. Whether a player has a line is read from the whole season, so a position or team filter never makes one who played look absent; the filters on rows hold by what the table says (its team, its position, the players named). These rows join the box-score rows (`base`) with their sums NULL, before the rows are summed, and that table's `publishedCte` reads its counts over both, so a player with a regular-season line who missed the whole playoff run has both counted over the two season types. Every other table, built, model or published, still reads over `base` alone. The row's name, team and position come from its box-score rows wherever it has any, else from the table's: the name from the player table first, the position from the roster, else from the player's own line in the season's other type (Luka Dončić, out of the whole 2025-26 playoff run, has no roster row that season and reads his regular season's), else NULL. A row with no line carries `no_line`, comes back as `noLine` on the result's row, and its every `q` flag is false: it never qualifies, ranks, takes a percentile or enters the league's mean, which is read from the league's own sums without these rows. Sorted by such a count, the rows with a sample come first in order of it, as a shrunk sort's do; the column comes back marked `addsRows`. A query that reads no metric of such a table compiles to the same SQL as before. A filter that splits a season (dates, the last games, opponents and the rest) gives these metrics their reason, "Published for whole seasons only.", and a split within games "Not counted from the play by play, so it has no split.", so nobody is added there either: games out are counted per season, and a player with no line has no games for a range to cut.

SportsDataverse's impact models (Plan T707) are two more, from `src_nba_impact`, players only. `pub_player_impact` stores RAPM, adjusted RAPM and their parts times the possessions they were fitted on (offense, defense, or both for the total), SPM and BPM and their parts times minutes, and WAR as published: 21,117 rows, 1996-97 on, regular season and playoffs. `pub_player_darko` stores DARKO's skill, next-season projection and its spread times games, from the regular season only, since the playoff rows repeat it: 14,586 rows, 1997-98 on. The 16 metrics are in `src/shared/stats/catalogue/impact.ts`, in an Impact (SportsDataverse) family. Every label ends "(SportsDataverse)", every column head "SDV", and every description says it is the dataset's calculation, not the model authors' figure. DARKO is a state at the season's end, not a total or a rate, so its metrics carry `oneSeason`: the engine answers them for one regular season at a time, and otherwise null with "Published for one season at a time." or "Published for the regular season only.". Grouped by season, each season answers. A season's leaderboard with ten box-score columns and twelve impact ones answers in 170 ms (median of seven), against 103 without on the same run; all twelve over every season from 1996-97, grouped by season, 209 ms.

The engine sums a published table apart from the box scores and joins the result by row, so neither multiplies the other. A row's name, team, position and `games` still come from the box scores.

### Game tables

A published metric can also name a built table at game grain in `publishedGames`. Under any filter that splits a season (a date range, the last games, home or road, an opponent, a team, a grouping by game, month, team or opponent) the engine reads that table instead of answering "Published for whole seasons only."; a whole season still reads the `published` table. The surface is three pieces, kept small for the tables that follow:

- **The table** is built by a step like any other, with one row per game and whatever the row is about (a pair of players for `game_matchups`). It holds `game_id`, keyed to `game` (D27), the column the engine sums by (the player's or team's id), and counts only, named as the `published` table names them, so the metric's one formula reads either. Rates are divided on read.
- **The registry**, `src/main/stats/derived/gameTables.ts`: each table's name, entity, `key` (its column holding the player or team id) and `components` (what the engine may read). `games` is the one special component: the engine counts the distinct games with a row rather than summing a column. `grainsOf` gives a published metric the game grain when its game table holds every part of its formula.
- **The engine** (`gameCte` in `engine/compile.ts`) joins the table to the box-score rows in scope (`base`) by `key = player or team id` and `game_id = game`, sums the components per output row and per group, and left-joins that to the box-score sums on every grouping dimension. Every filter on a game holds because `base` already applied it, and the last games are the player's or team's last appearances, as for box-score metrics. The gaps keep their order: coverage first ("Recorded from 2017-18."), then a divisor the game table lacks ("Published without minutes."); the season types a published table lacks do not apply, since the game table holds every type it has rows for.

The consequence to know: a row of the game table counts only where the box score has the player in that game. For `game_matchups` that leaves out 34 defender-games of 2017-18 to 2025-26 where tracking assigned a player the box score lists without minutes (`nba-data-sources.md`).

`game_matchups` (Plan T906) is the first: 2,197,055 rows, one per game, player on offense and defender, from `src_nba_game_matchups`, built by `derived/gameMatchups.ts` in the `stats:published` step, which a refresh runs again once at its end when an events-tier source it reads (`PUBLISHED_LATE_SOURCES`) wrote rows, before `stats:plays`. Its 17 defender metrics are the Matchups family's except the shares by position. A season of defenders through a date range answers in 44 to 145 ms. `readGameMatchups` reads a game's pairs from it, and `readScopedMatchups` a player's pairs over any scope that is not a whole regular season (`matchupReads.ts`).

### A file older than the build

A new build can add a column to a game or season table, or a new published or model table, before the league's file has been refreshed. The next refresh builds it, which for a college file takes minutes (the upgrade from 1.3.0, under "Measuring a real load"). Until then the screens read the file as it is.

**What was checked against the file, and what was assumed.** Before this rule, every gap the compiler gave (`gapOf`) was decided without looking at the file:

- `m.unavailable` and the coverage reasons come from the catalogue and the league's registry;
- `leftOutGap` comes from the releases this build leaves out (`leftOut.ts`);
- `notBuiltYet` comes from the steps a league's refresh has (`League.builds`), not from what a file holds.

The one check against the file was at run time, and only for the attribute tables (`missingTables` in `run.ts`). `Have` (`inspect` in `derived/sql.ts`) is the builders' view of the file. It lets a build read a source column that is missing as NULL, and the engine never saw it. So the compiler assumed that every component column of `player_game`, `player_season`, `team_game` and `team_season`, and every published and model table with its columns, was in the file. A 1.3.0 college file asked for the half splits made DuckDB fail on the missing column, and the whole query failed with it.

**The rule.** The service reads the file's tables and columns once per worker, and again after each build step of a refresh, so a new metric answers as soon as its table is built (`readFileSchema` in `run.ts`, from `duckdb_columns()` and `duckdb_tables()`). The compiler checks each metric's components and its divisor against that, after the gaps above:

- a component of the metric's own table (its model table, its built game table or its published table) must be a column of that table;
- every other component must be a column of the entity's box table at the query's grain;
- an own table with no rows is not built yet either, since opening a file creates the published, play and model tables empty. The league's coverage is checked first, so an empty table never hides a season the league does not have.

A metric that fails reads null with "Built at this league's next refresh." for that metric alone; the rest of the query answers and sorts as before. An attribute filter whose column the file lacks reads "Age: Attributes are built at the next refresh of this league." and answers no rows, like any other filter gap (D51). The components are the physical column names, so the check needs no list of its own. On files built by the current recipe it gives no reason: none of a college file's components is missing, and a WNBA file lacks only the college-only components, which have coverage reasons already.

**Three reasons of one family.** Each is given for the metric alone, after the catalogue's own gaps:

| Reason                                                           | What it means                                                                       | Read from                                        |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------ |
| "Built at this league's next refresh."                           | The file holds the source, but the table or column a metric reads is not built yet  | The file's tables and columns (`readFileSchema`) |
| "Not published yet for 2026-27 (last looked for on 2026-11-24)." | The season under way has no file of the metric's source yet; the refresh asks daily | `source_state` and `sync_log` (`sourceSeasons`)  |
| "No file published for 2019-20."                                 | A finished season in the metric's stated coverage has no file: none will come       | The same                                         |

- **The published sources only:** the last two are for published metrics. A source the file holds no season of has its own reason (left out, or not loaded yet). A source of one file for every season, and a league with no published tables, get neither.
- **A release of many files** into one table (play types, hustle, matchup rollups) keeps a `source_state` row per file. Its table holds a season when any of its files does.
- **A scope of several seasons:** when some seasons hold a file, the metric answers for those, and the query's notes name the others in the same words.
- **On the real load** (the NBA and the WNBA refreshed on 2026-11-23, `~/.cache/metis-dev/t1703-boban`), every published metric's source matched: 604 NBA metrics and 155 WNBA metrics. No metric has a finished season without a file. Only `nba_current_impact` has no file yet for 2026-27 (9 metrics).

## Attributes and filters

D51 (Plan T1701.1). What Metis knows about who a player or a team is, in tables of its own, and the conditions a query can put on it or on any metric.

### The registry

`src/shared/stats/attributes.ts` lists every attribute: id, label, a sentence, entity, type (number, text, date, enumeration, flag), unit, group, its table and column, its sources in the order they are read, and its coverage per league (a first season, a last where a source stopped, or why the league has none). 58 at first, 48 of players and 10 of teams. They are not metrics: they have no sample and no rank, are not summed over games, and are not in the catalogue.

### The tables

Built by `src/main/stats/derived/attributes.ts` in each league's file, by the worker alone (rule 3), at the `stats:attributes` step: after the game tables, and again after the published tables (the bio and the combine are in the published tier). The step has its own version (`ATTRIBUTES_VERSION`), so a change of rules rebuilds them with nothing downloaded, and it logs nothing before the identity tables exist. Measured on the clean four-league load: 0.43 s (NBA), 0.21 s (WNBA), 0.59 s (NCAA Men), 0.50 s (NCAA Women).

| Table                      | One row per                                                            | Rows (NBA, WNBA, NCAA Men, NCAA Women) |
| -------------------------- | ---------------------------------------------------------------------- | -------------------------------------- |
| `player_attributes`        | Player of `player`                                                     | 3,602; 1,240; 43,481; 31,740           |
| `player_season_attributes` | Player and season with a counted game or a line on the league's roster | 16,586; 5,067; 57,058; 45,844          |
| `team_attributes`          | Row of `team` (a team in a season)                                     | 1,005; 380; 4,287; 3,760               |

What each reads, in order (policy 5: where two sources publish one fact both are kept, `_roster` and `_espn`, and the plain column reads them in this order):

- **Birth date:** the league's roster ("MAR 30, 2003"), else ESPN's athlete file or rosters ("2003-03-30T08:00Z", midnight in the United States written in UTC, so the date part is the day). They differ on 46 of the NBA's 2,645 players both hold, 19 of the WNBA's 820; the colleges have ESPN's alone.
- **Birthplace, state and country:** ESPN's athlete file, else its rosters. **Country:** the league's bio (NBA, WNBA), the country it lists a player under, which can differ from the birth country.
- **School:** the league's roster, else the bio's college. **Hometown and high school:** stats.ncaa.org's team rosters, through `ncaa_player_ids`.
- **Height and weight as last published:** the league's or the college roster ("6-11", the college's inches), else ESPN ("6' 5"", "205 lbs", or its numbers). Heights differ on 274 of the NBA's 2,645 players held by both (36 by more than an inch), 48 of the WNBA's 819, 1,689 of NCAA Men's 13,795. **That season:** the same sources for the season.
- **Draft:** the league's draft by the draft's own year (the NBA labels a file by the season after, `League.eventYear`), else ESPN's athlete file, whose pick is the overall pick and whose 0 is none: it holds the drafts before the league's files (1996 in the NBA). On the NBA's 1,609 players both hold, 61 differ in year or pick. Pick in round, team and where from are the league's alone. **Undrafted:** true where the bio says "Undrafted", or where no draft lists them though their first season comes after the draft file's first draft; NULL before it, never guessed.
- **Combine:** the latest combine a player went to, from the anthropometric and athletic testing tables the profile reads; `-1` (several without an id) is left out. The shooting drills stay on the profile.
- **Career:** first and last season from `player`; seasons played, the seasons with a counted game; season number, that season's place among them, NULL for a player already playing in the league's first loaded season.
- **Season:** the last team of the season from the season table; jersey and listed position from the league's roster, else stats.ncaa.org's, else ESPN's; experience from the league's roster alone ("R" is 0), since ESPN counts it another way (LeBron James reads 21, 23, 23 over three seasons mixed) and in college its count is a class year (kept as `experience_espn` in the professional leagues); class from stats.ncaa.org ("---" is none), else ESPN's "Freshman" in the same words; how acquired from the league's roster. The roster's line is kept as published (`roster_*`, `on_roster`) for the profile.
- **Teams:** code, name, conference and division from `team`; city from the league's crosswalk, else ESPN's location (none in college, where ESPN's location is the school's name); arena, its city, state and seats from ESPN's schedule, the venue of most home games that season with neutral sites left out; head coach from the league's coaches ("Head Coach" and "Interim Head Coach"), several joined by " / "; first season in the data; Division I from the groups file.

No source publishes handedness. Logos, headshots and team colours are left out (D31).

### Age

Worked out when read, never stored: whole years on a reference day in the season's final year (`AGE_REFERENCE`), January 31 in the NBA and the colleges and July 1 in the WNBA. January 31 is Basketball-Reference's glossary, "player age on January 31 of the given season" (read 2026-11-23). Its WNBA pages count a later day: on 2026-11-23, Diana Taurasi (born June 11) read 38 in 2020 and Nneka Ogwumike (born July 2) 29, which puts it from June 11 to July 1; Arike Ogunbowale, Breanna Stewart and Sabrina Ionescu agree. July 1 is taken inside that window, the exact day not proven. A row grouped by season reads its season's day; otherwise the latest season of its rows in scope. ESPN publishes few college birth dates (14 % of the men's Division I players in 2021-22, 1 % in 2026-27; 4 % and 0 % of the women's), so age answers for few college players and the rest are counted as having no value.

### Filters

`StatsQuery.filters`: at most 20 conditions, all of which hold, each `{ attribute | metric, op, value }`.

| Type                 | Operators                                                              |
| -------------------- | ---------------------------------------------------------------------- |
| Number, and a metric | between, at least, at most (both ends included), has a value, has none |
| Date                 | the same, with YYYY-MM-DD                                              |
| Enumeration          | any of, none of (letter case ignored), has a value, has none           |
| Text                 | any of, none of, contains (letter case ignored), has a value, has none |
| Flag                 | is, is not, has a value, has none                                      |

- **After the ranks:** the compiler (`engine/filters.ts`) adds `judged`, each ranked row with whether it passes and whether it lacks a value a condition needs, and `filtered`, the rows that pass, and every form of the answer (a list, many rows, `places`) reads from it. So a row keeps its percentile and rank among every row, the list is 1 to n of those left, `total` counts them and the limit applies after. A query with no filters reads `shaped` as before: its SQL is unchanged (`nbaSqlUnchanged.test.ts`, and a test that `filters: []` compiles to the same SQL).
- **Attributes** are joined by the row's id: `player_attributes` by player, `player_season_attributes` and `team_attributes` by player or team and the row's season (its group's when grouped by season, else the latest season of its rows in scope).
- **Metrics** compare the value as the transform shows it (`t<i>`, `MetricValue.value`): per game under per game, a percentile under percentile, a percentage as a fraction. A metric the query does not list is compiled after its own metrics, for the condition alone, and not shown (`Compiled.shown`).
- **No value:** a row lacking a value a condition needs is left out. It is counted in `StatsResult.filtered.noValue` when it passes every condition it has a value for: a row the conditions cannot place, not one a condition with a value rejects (with "experience 0 and height at least 82", a veteran with no height is not counted). Counted among the rows the board would list (the qualified ones under "Qualified only"); has a value and has none count nothing. A rookie is experience 0 where the roster lists the player and has no value where it does not (LeBron James has no 2025-26 roster line), so a filter on experience leaves those players out and counts them. With no row left, the count is read on its own.
- **No answer:** a condition on an attribute the league does not have, or has for none of the seasons in scope ("Arena capacity: published from 2001-02 to 2018-19."), or on a metric with no answer to the query (its column's reason), answers `filtered.reason` and reads nothing; so does one on a file whose attribute tables are not built yet ("Attributes are built at the next refresh of this league.").
- **Values are bound,** never written into the SQL; text is compared lowercased.
- **The scope filters** (`positions`, `teams`, `places`) are unchanged. `places` could later be one more condition (an id any of), but it answers a different question, a row's place in the unfiltered order, so it stays.

## Models

Plan Stage 10: tables Metis computes in TypeScript, by a solve or a sequential pass, from the game tables. Everything here is labelled as computed by Metis (`kind: 'model'`, a source of "Computed by Metis from …"). The code is in `src/main/stats/models/`: pure maths (solvers, formulas) in files with no database import, tested with worked values (`linear.ts`, `srs.ts`); one file per task that reads the database and returns rows (`teamStrength.ts`); and `build.ts`, the registry and the step.

Six builders, in `MODEL_BUILDERS` order, each a section below: team strength (`team_strength`, T1001), the box-score composites (`player_composite`, `team_composite`, T1005), Elo (`elo_game`, `elo_wins`, `elo_schedule`, T1002), the adjusted ratings (`adjusted_rating`, T1004), the season forecast (`team_forecast`, T1003) and metric stability (`metric_stability`, T1006), which reads every table before it through the engine and so comes last. On the Stage 10 gate's first load from nothing the step ran last, after `stats:plays`, and wrote 372,222 rows in 200 seconds: Elo 169,328, team strength 78,238, the adjusted ratings 78,218, the composites 26,488, the forecast 18,498 and stability 1,452. Each builder's computing time over every season, timed apart on a copy (the rest of the step is writing the rows): the forecast, which simulates 20 snapshots of every season from 1995-96, about 57 s on a quiet machine, stability about 38, the composites 3.5, the adjusted ratings 2.6, team strength 1.0 and Elo 0.7. A daily refresh with the season in progress changed recomputes 2026-27 alone in about 4 seconds, the forecast's 10,000 runs of the season most of it, and keeps the stability rows; a day with no file changed does not run the step. `scripts/check-rebuild.mjs` compares the model tables too, and two loads of the same data give equal ones, the seeded simulation included.

### The `stats:models` step

The last step of a refresh, after `stats:plays` (`runModelsBuild` in `sync.ts`), logged as `stats:models`. It runs when:

- a file of any tier wrote rows: `markModelSeason(season)` records `models:<season>` in `derived_state` as it loads, before anything can stop the build. A file of every season (season 0) marks the season in progress, not every season: of the eight such files, `espn_games_in_repo` and `espn_schedule_master` changed twice in a week of loads (between Nov 7 and 10 and between Nov 11 and 13, 2026) and `player_aliases` once, the other five never, and what they add is this season's games and players. Marked as every season they would recompute every model each time (`markModelSeason(db, 0)` still means every season, for code that needs it);
- `MODELS_VERSION` changed (`derived_state` row `models`): every builder recomputes every season;
- a builder is new, its `version` changed (`model:<name>`) or one of its tables has another shape: that builder recomputes every season;
- the last run failed: the `models:<season>` rows are cleared only when a run finishes, so the next refresh runs it again with nothing downloaded;
- the game tables were rebuilt because their recipe or the identity changed (`derivedStale` in `sync.ts`): every builder recomputes every season.

**After a recipe change that only adds columns.** The last rule recomputes the models even when the new recipe only adds columns no model reads. Measured on the upgrade from 1.3.0 (2026-11-24, below): the college game recipe went from version 4 to 6 for the half and transition splits and the seconds per possession, and the models then took 301 s for the men and 263 s for the women, against 167 s and 113 s for the game tables themselves. It is left as it is. The step cannot tell which columns a builder reads (a builder reads the game tables through its own SQL, with `have` for what is present), and a recipe change may also change the values of columns that are there already. Recomputing every season is the one rule that is right for both. It costs one long refresh per recipe change, and the screens answer from the file throughout, since each read has its own connection.

It waits until `game`, `team`, `team_game` and `player_game` exist. A sealed season whose files did not change is never recomputed, so a daily refresh computes the current season (and any season whose files changed) only.

**Builders.** `MODEL_BUILDERS` is an ordered list; each Stage 10 task appends one line and owns its tables and files. A `ModelBuilder` has:

| Field     | What it is                                                                                                                                                                                                                                                                                                                                |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`    | Its key in `derived_state` (`model:<name>`)                                                                                                                                                                                                                                                                                               |
| `version` | Bump when its rows change: the next refresh recomputes every season of its tables, and no other builder's                                                                                                                                                                                                                                 |
| `tables`  | Its `ModelTable`s (below)                                                                                                                                                                                                                                                                                                                 |
| `seasons` | Optional: the seasons to compute given the seasons whose data changed and the seasons played. A model carried from season to season (Elo) adds the seasons after them (below)                                                                                                                                                             |
| `build`   | `(ctx) => rows`: one season's rows for each of its tables, as objects keyed by column name. `ctx` gives `db`, `have` (the tables and columns present), `season`, `current`, and `changed` (the seasons whose data changed for this builder, every season played when it recomputes all). Null keeps the season's rows as they are (T1006) |

The step calls `build` once per builder and season, then replaces that season in one transaction: its rows deleted from each of the builder's tables and the new rows inserted (in batches of 500), so a reader sees a season old or new, never half. Builders run in order, and a season one builder recomputes is recomputed by every later builder too, so a builder can read an earlier builder's table. A builder recomputing every season also drops the seasons no longer played. A missing source table or column must not fail a build (data policy 4): read `have` and return NULL, or no rows.

**Tables.** A `ModelTable` declares how the engine reads it:

| Field                      | What it is                                                                                                                                                                                                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `table`, `entity`          | The table's name; `player` or `team`                                                                                                                                                                                                                                                                                                        |
| `kind`                     | `sum`: counts and sums, each rate a numerator and a denominator (data policy 3), added over the rows in scope like a box score. `state`: a value that is not a sum (a rating), the value after each game, read at the last game in scope. `meta`: a table about the metrics, read by the service and never by a metric (`metric_stability`) |
| `grain`                    | `game`: a row per player or team and game. `season`: a row per player or team, team and season type, read for whole seasons only. A state is always at game grain                                                                                                                                                                           |
| `columns`                  | Every column, typed, in order: `season INTEGER, game_type VARCHAR, team_id BIGINT`, then `player_id BIGINT` on a player table, then `game_id VARCHAR, game_date DATE` at game grain, then the values                                                                                                                                        |
| `components`               | The value columns a metric reads as `{name}`; never a key                                                                                                                                                                                                                                                                                   |
| `gameTypes`, `typesReason` | The season types it has rows for, and the reason a scope with none of them reads instead                                                                                                                                                                                                                                                    |

A player's row is per team, never a total of their teams: the engine adds a traded player's teams itself, once. **A `state` table never holds a game not played:** at season grain the engine joins it by season and season type, not by game, so a game to come would be the last row in scope and its empty value would blank the season (Elo read "—" for all of 2026-27 until its games to come moved to a table of their own). Games to come go in a table no metric names. The tables are created empty on every open (`modelsBootstrap`), so a query before the first build reads null, not a missing table.

### How the engine reads them (`model`)

A metric names its table in `model`, the one field Stage 10 added to `MetricDef`. Its formula reads the table's components and, for anything the table does not hold (`games`, `minutes`, `box_games`), the box-score sums of the same rows, as a `built` metric does. `grainsOf` gives it both grains, or the season only for a `sum` table at season grain, and none when a component is in neither.

- **A `sum` table** is read as a `built` table is ("Metrics on a built table"): joined to the box-score rows in scope, by game at the game grain, by season, season type and (with teams named) the row's team at the season grain, so a date range, the last games, home or road and every other filter on a game read exactly, and a traded player's teams are added once. A table at season grain under a filter that splits a season reads null with "Computed for whole seasons only.". Transforms (per game, per 36, per 100) divide as for any `sum` metric.
- **A `state` table** (`stateCte`) is read at the last game in scope of each output row: `arg_max_null(value, (game_date, game_id))`, so a value that is null after the last game (no games left) stays null rather than reading an earlier game's over the table's rows joined to the box-score rows in scope, by game at the game grain, by season and season type at the season grain. So a whole season reads the rating after the season's last game, a date range ending mid-season the rating as it stood after the team's last game in it, grouped by game the rating after each game, by season each season's final. Over several seasons at once it reads null with "A rating as of a game, read one season at a time." unless grouped by season or game. A state metric is `aggregation: 'ratio'`, so no transform divides it, and a screen at the game grain notes "<label>: as of the last game in scope.".
- **Season types.** A scope with none of the table's `gameTypes` reads null with its `typesReason` ("Solved on the regular season."). A scope with some reads the rows of those.
- **Splits.** A model is computed per game, so under `scope.split` it reads null with "Computed per game, not per moment, so it has no split.".
- **Coverage.** `firstSeason` gives "Recorded from …" outside it, as for every metric.

**A model carried from season to season** (Elo, with its regression between seasons) returns from `seasons(changed, played)` every played season from the earliest changed one on, so a change in 2019-20 recomputes 2019-20 to now. Its `build` for a season reads the prior season's final state from its own table (`SELECT … FROM <its table> WHERE season = <season − 1>`, each team's last row by `game_date`): the step computes seasons in order, one transaction each, so that row is already the new one, and an older sealed season's rows stand from the run that wrote them. The first season it has (1993-94) starts from its own rule. It must not read a later season, and a full recompute (a new `version`) runs every season in order the same way.

### How to add a model table

1. Write the maths in a file of its own with no database import, and test it with values worked by hand (`tests/main/stats/models/`).
2. Write the task's file in `src/main/stats/models/`: its `ModelTable`s, and a `ModelBuilder` whose `build` reads the season (from `game`, `team_game`, `player_game`, an earlier builder's table) and returns rows. Keep to the column order above.
3. Append one line to `MODEL_BUILDERS` in `build.ts`. Do not bump `MODELS_VERSION`: a new builder, its own `version` or a new shape is enough.
4. Add the metrics to the family's catalogue file with `model: '<table>'`, `kind: 'model'`, sources naming Metis, the right `firstSeason`; a state as `aggregation: 'ratio'`, a sum as numerator and denominator. Add a worked row for the catalogue test (`MODEL_ROW` in `tests/shared/stats/catalogue.test.ts`).
5. Test the builder on a small fixture through `buildModels` and the read through `runQuery` (`tests/main/stats/models/build.test.ts`, `tests/main/stats/engine/models.test.ts` show both), then run a real refresh and time the step.

### Team strength (Plan T1001)

`team_strength` (`models/teamStrength.ts`, builder version 2): a `state` table of the regular season, one row per team and game day from 1993-94, the season so far after that day's games, everyone's included: `srs_games`, `mov` (average margin), `sos` (average SRS of the opponents played, one term per game), `srs`, then `games_left` and `sos_left`, the team's regular-season games after that day and the average SRS, as of the day, of their opponents (an opponent with no game yet counts as 0; null once none are left). Each day's ratings are solved directly, not iterated (`srs.ts`): games × rating − Σ opponents' ratings = Σ margins for each team, with one equation of each group of teams that have met replaced by "the ratings sum to zero", so each day's league mean is zero and SRS = MOV + SOS exactly. The game table's type leaves out the All-Star games ESPN files as regular season and the Cup final, which is not a regular-season game; the other Cup games count. The games left are the later games played and, in the season in progress only, the games on the schedule not played yet, whatever their listed date (a postponed game is still to come); in a past season a game never played was cancelled (Boston at Indiana, 2013) and is not left.

The Ratings family (`catalogue/ratings.ts`) reads it as `team_srs`, `team_sos`, `team_sos_left` and `team_games_left`, and has five metrics from the scores in scope, exact over any scope, playoffs included: `team_mov` (points for less against per game), `team_pyth_pct` (points for to the 14th over both to the 14th, Basketball-Reference's exponent), `team_pyth_w` and `team_pyth_l` (that share of the games decided) and `team_win_resid` (wins less Pythagorean wins, described as a residual, not as luck). `team_point_diff` (Traditional) is the same margin as a total. A playoff scope reads SRS and the schedule strengths as "Solved on the regular season.".

Measured on a copy of the Stage 9 gate load (`scripts/load-report.mjs`): computing every season (34, 78,238 rows) takes 19.3 s (10.6 s before the games left were counted); a day with 2026-27's files changed recomputes 2026-27 alone in 0.12 to 0.28 s (340 rows, two runs); a day with no file changed does not run the step. Checked by `scripts/check-team-strength.mjs` (in [nba-data-sources.md](nba-data-sources.md), "Team strength").

### Box-score composites (Plan T1005)

`player_composite` and `team_composite`: `sum` tables at season grain, one row per player (or team), team, season and season type, the regular season and the playoffs, from 1993-94. The builder (`boxComposites.ts`) reads each season's player lines from `player_game` and the teams from `team_season`, and the pure formulas compute the rest (`box.ts`, `oliver.ts`, `per.ts`, `winShares.ts`, `bpm.ts`, `composites.ts`, each tested on LeBron James's 2016-17 worked by hand):

- **Oliver** (Basketball-Reference's "Calculating Individual Offensive and Defensive Ratings"): `sc_poss`, `tot_poss`, `pprod`; `stops`; `d_poss` (the team's defensive possessions while on the floor, Stop%'s denominator) and `drtg_num` (DRtg × `d_poss`).
- **PER** ("Calculating PER"): uPER with the league's factor, VOP and DRB%, times league pace over team pace, scaled so the league's minutes-weighted mean is 15: `per_num` (PER × minutes).
- **Win Shares** ("Calculating Win Shares"): `ows`, `dws`, `ws`; marginal points per win are 0.32 × the league's points per team-game × team pace over league pace.
- **BPM 2.0 and VORP** ("About Box Plus/Minus"): the position (1 to 5) and offensive role (1 to 5) regressions on the player's shares of the team's counts while on the floor, each blended with 50 minutes of the listed position (a guard 1.5, a forward 3.5, a center 5) or of role 4, then shifted per team to a minutes-weighted mean of 3 within 1 to 5; the published coefficient tables, sliding with position (the scoring and usage terms with role); points re-valued at a baseline of 1.00 a true shot attempt; rates per 100 team possessions on the floor; then one constant per team so the players' values weighted by their share of the floor time add up to the team's adjusted rating. `bpm_num` and `obpm_num` (× minutes), `vorp` = (BPM + 2) × share of the floor time × team games / 82, and `position_num`, `role_num` (× minutes).
- `cmp_minutes`, the minutes those lines hold, divides every per-minute value.

Every value is a sum, or a value times its weight beside the weight (data policy 3), so a traded player's season, a career or any group of whole seasons divides back exactly. A traded player's stints are each computed with their own team, as the published methods do; the engine adds them. Basketball-Reference's combined row for a traded player weights PER and BPM by minutes, which is what the stored parts give.

**Team totals** are the box-score games, the same games as the player lines, with **team turnovers** added to the team's and the opponents' turnovers, as Basketball-Reference's team totals and possessions count them: the NBA's play by play's `tov_team` from 1996-97, and before it ESPN's team box score's `team_turnovers − turnovers`, which equals the play by play's count on all but 3 of 8,508 team-games of 1996-97 to 1999-2000. Without them league possessions read 0.6 % low (2016-17: pace 95.8 against the published 96.4) and every player's OWS about 0.3 low. Possessions are Basketball-Reference's estimate from season totals (`box.ts`), not the summed per-game `poss_bref`.

**Calls the method leaves open,** each written in the code: the team rating BPM adds up to is the net rating per 100 possessions plus the opponents' strength (the mean, over the team's games of that type, of each opponent's final regular-season SRS from `team_strength`, converted to points per 100) and half the lead effect, 0.35 / 2 per point of average lead, with the average lead estimated as half the margin per game; OBPM's target takes half of both adjustments. The regular season and the playoffs are each computed against their own league totals.

**The engine** reads them through `model` (above): whole seasons only, "Computed for whole seasons only." under a date range, the last games or any filter that splits a season, and "Computed for the regular season and the playoffs only." for the play-in, the Cup final and the rest. The metrics are the Box-score ratings family (`src/shared/stats/catalogue/boxComposites.ts`): PER, OWS, DWS, WS, WS/48, BPM, OBPM, DBPM, VORP, points produced, possessions used, scoring possessions, floor percentage, individual offensive and defensive ratings, stops, stop percentage, the stored position and role, and the team sums of Win Shares, offensive and defensive Win Shares, VORP and points produced. Win Shares and VORP stay totals under every mode (`totalOnly`).

**Speed:** the builder computes every season in 3.6 s, and the step wrote its 26,488 rows in 10.5 s in all on a real refresh; a daily refresh with the current season changed runs the whole models step, T1001's builder included, in 0.6 s. Its team query reads `team_season` and joins only `team_game`'s keys for the turnovers: scanning `team_game`'s thirty summed columns took a quarter of a second a season, and so did the turnovers' CTE inlined twice, so it is materialized. Every read is under 300 ms (`scripts/check-composites.mjs`).

### Elo (Plan T1002)

`models/elo.ts` is the maths, `models/teamElo.ts` the builder `team_elo` (version 3), carried from season to season as "A model carried from season to season" above describes: its `seasons` recomputes every played season from the earliest one changed, and each season starts from the season before's final ratings read back from its own table.

**The model** is FiveThirtyEight's published NBA Elo with two values fitted: win probability `1 / (1 + 10^(−edge/400))`, the edge the rating difference plus home court; K 20; the margin multiplier `(|margin| + 3)^0.8 / (7.5 + 0.006 × the winner's edge)`; the expected margin the edge over 28. Home court is 80 Elo points rather than 538's 100, and between seasons a rating keeps 0.65 of its distance from 1505 rather than 0.75: fitted on 1995-96 to 2009-10 and scored on 2010-11 on, they lower the Brier score by 0.0018, eleven standard errors ([nba-data-sources.md](nba-data-sources.md), "Elo"). Every team starts at 1500 in 1993-94; a new franchise enters at 1300 (Toronto and Vancouver in 1995-96, Charlotte in 2004-05). A franchise keeps its rating under the `team` table's id, which follows Seattle to Oklahoma City, Vancouver to Memphis and New Jersey to Brooklyn; the Hornets' move from Charlotte to New Orleans in 2002 is under two ids, so a season with exactly one team new and one team gone links the two (`seasonStart`). Charlotte's id returning in 2004-05 after two seasons away is a new franchise.

**The games:** every game between two teams of the league in date order, then by id: regular season, play-in, playoffs and the Cup final; All-Star and preseason games never. Home court is 0 at a neutral site, read from ESPN's schedule by `neutralSitesSql` (`models/neutral.ts`, a subquery of `game_id, neutral` that any model can join): its `neutral_site` (games abroad from 2012-13, the Cup's semifinals and final from 2024-25), the Cup final and a semifinal by ESPN's note (2023-24's semifinals are not marked), and the 2020 bubble by its city, Lake Buena Vista (not marked either). The 11 games abroad before 2012-13 carry no mark and keep home court. In the season in progress the games not played yet are rated after every game played, with the latest ratings, whatever their listed date.

### Adjusted ratings (Plan T1004)

`adjusted_rating` (`models/adjustedRatings.ts`, builder version 2; the maths in `models/adjusted.ts`): a `state` table of the regular season, one row per team and game day from 1993-94, the season so far after that day's games, everyone's included: `adj_poss` (the team's possessions), `adj_ortg`, `adj_drtg`, `adj_nrtg`, `adj_league` (the league's points per 100 possessions) and `adj_home` (home court).

Each game is two observations, one per offense: points per 100 possessions = mean + the offense's effect + the defense's effect on points allowed + home court (+h for the home offense, −h for the road one, 0 at a neutral site), weighted by the game's possessions, so the fit is the one a row per possession would give. A ridge prior of 250 possessions on each team effect (`RIDGE_POSSESSIONS`) pulls it toward 0, as if every team had also played two and a half games of league-average basketball; the mean and home court have none. Predicting each day's games from the fit as of the day before over every season (`scripts/check-adjusted.mjs`, section 4), 1,000 possessions does a little better (10.535 points per 100 of error against 10.609, and 11.125 with no prior), but it pulls a season's final ratings a tenth of the way to average, and these sit beside the plain ratings and SRS as a record of the season; 250 moves them about 0.12 points per 100 and still steadies the first weeks. With it the effects of each side sum to 0, so the ratings are the league's points per 100 plus the effect: adjusted ORtg = league + offense effect, adjusted DRtg = league + defense effect (lower is better), adjusted NRtg = their difference, and the teams' mean of each is the league's. `adj_home` is twice h: the net points per 100 a team gains at home over a neutral floor. Each day's normal equations come from running sums and are solved directly (`linear.ts`), with the effects of each side held to a zero sum by two Lagrange rows, which a prior already satisfies and which pick the centred solution without one.

- **Possessions** are the box-score estimate the plain ratings divide by (`team_game.poss_sym`, the mean of both teams' simple estimates), and the points are the box score's, so the adjusted ratings sit on the plain ratings' scale. A game without a box score on both sides is left out (5 in 1993-94, 5 in 1995-96, none since).
- **A neutral site** is read by `neutralSitesSql` (`models/neutral.ts`), the same games Elo gives no home court: ESPN's `neutral_site` mark, the Cup semifinals by ESPN's note (2023-24's are unmarked) and the 2020 restart by its city, Lake Buena Vista. The Cup final is not a regular-season game, so not fitted.
- **Games:** the regular season as the game table types it, so not the All-Star games ESPN files as regular season or the Cup final. A playoff scope reads "Solved on the regular season.".

The Ratings family reads it as `team_adj_ortg`, `team_adj_drtg`, `team_adj_nrtg` and `team_adj_home`, each described as a model computed by Metis, not the NBA's or any publisher's figure.

Measured on a copy of the Stage 9 gate load (`scripts/load-report.mjs`): this builder alone computes every season (34, 78,218 rows) in 12.8 to 12.9 s (three runs; 14.3 to 14.6 s before its read took the season's rows of `team_game` first, ten times faster than joining the table whole); a day with 2026-27's files changed recomputes 2026-27 with both builders in 0.21 to 0.22 s (680 rows, three runs). Checked by `scripts/check-adjusted.mjs`, with the comparison against SRS (in [nba-data-sources.md](nba-data-sources.md), "Adjusted ratings").

### Season forecast (Plan T1003)

`models/forecast.ts` is the builder `season_forecast` (version 1), after Elo's in `MODEL_BUILDERS`. The pure code: `standings.ts` (a season's records, the NBA's tie-break procedures and each era's seeding), `playoffs.ts` (the play-in, the bracket, best-of series with their home patterns), `simulate.ts` (the runs) and `random.ts` (a seeded generator, so a run repeats). The rules per era and the check that they reproduce every real playoff field are in [nba-data-sources.md](nba-data-sources.md), "The playoff field, per season".

**A run** plays the rest of the regular season from each team's Elo rating as of the day: the games played after it in a past season, and in the season in progress the games still to come from `elo_schedule`, whatever their listed date. Each game's winner is drawn with the Elo win probability (home court 80, none at a neutral site) and its margin from a normal around the Elo expected margin with a spread of 12.4 points (12.38, the regular season's margins around `exp_margin` from 1995-96 to 2025-26), cut on the winner's side, so the winner keeps exactly the Elo probability and point differential, a tiebreaker, has a margin to read. The ratings move after every simulated game by Elo's own update, margin multiplier included, so a team that gets hot in a run stays hot in it. The season in progress's games the schedule does not list yet (the Cup's 24, set by its group stage) are played against an average team at no home court, up to 82 a team, and count in the overall record only. Then the standings and seeds by that season's rules, the play-in (2019-20's or today's), and the bracket to the title, playoff games rated the same way (no home court in 2019-20's bubble).

**`team_forecast`** (state, regular season, from 1995-96 like Elo's metrics): a row per team and snapshot, holding `as_of` (the day, after its games), `runs`, `games_in` (the league's games played by then), `model_version`, `proj_w`, `proj_l`, `p_playoffs`, `p_top6` (from 2020-21), `p_play_in` (from 2019-20), `p_round2`, `p_conf_finals`, `p_finals`, `p_title` and `mean_seed` (the mean place in the conference's seed order before the play-in, 1 to 15).

**A forecast as of a date in a state table.** A state row is keyed by game, and a forecast by day. No shell change was needed: each snapshot's row sits on the team's last regular-season game on or before its day, with the day beside it in `as_of`, so the engine's state read (the row at the last game in scope) gives the latest forecast made by then. Two snapshots on the same game of a team (no game between them: the All-Star break, a pause) keep the later one. A season's whole regular season reads the last snapshot, the forecast after the last games; a date range reads the forecast as it stood; grouped by game, the snapshots.

**Snapshots:** one at each twentieth of a season's regular-season games (the day of its ceil(k × games / 20)-th game), so a quarter, half and three quarters of the season are among them, and in the season in progress the latest day too. A past season holds twenty snapshots of 500 runs each; the season in progress takes 10,000. **What 500 runs mean:** a probability counted over 500 runs has a standard error of √(p(1 − p)/500), at most 2.2 points (at 50 %), 1.3 at 10 % and 0.6 at 2 %, so a past season's odds are good to about two points: a title chance read as 12 % is 10 to 14 % within one standard error, and odds under 1 % rest on a handful of runs (one run is 0.2 %). The calibration by decile is not affected, since a decile is ten points wide. The season in progress's 10,000 runs bring the error under half a point (0.5 at 50 %). A refresh recomputes the season in progress's latest forecast and keeps its earlier snapshots while their games stand (`games_in` and `model_version` unchanged); a late score or a corrected game recomputes them.

The Ratings family reads it as `team_proj_w`, `team_proj_l`, `team_playoff_pct`, `team_top6_pct` (from 2020-21), `team_play_in_pct` (from 2019-20), `team_round2_pct`, `team_conf_finals_pct`, `team_finals_pct`, `team_title_pct`, `team_mean_seed` and `team_forecast_runs`, each described as a model's odds computed by Metis. A playoff scope reads "Forecast in the regular season, as of its games.". In the Ratings preset (twelve columns at most) projected wins and playoff odds follow MOV, SRS, Elo and the adjusted net rating; the Pythagorean percentage (which PYTH W repeats) and SOS left moved to the column picker to make room, with the rest of the forecast.

Measured on a fresh copy of the Stage 9 gate load (`scripts/load-report.mjs`): the builder alone computes every season in 60.6 s (18,498 rows, 32 seasons), and the models step with all five Stage 10 builders took 128.0 s; a day with 2026-27's files changed runs the whole step in 3.3 to 4.0 s (one forecast of 10,000 runs, the other snapshots kept). A season of 10,000 runs with a full schedule left takes 2.7 s, 0.44 s with none left. Reads 9 to 35 ms. Checked by `scripts/check-playoff-field.mjs` and `scripts/check-forecast.mjs` ([nba-data-sources.md](nba-data-sources.md)).

### Metric stability (Plan T1006)

`metric_stability` (`models/metricStability.ts`, the maths in `models/stability.ts`): one row per catalogue metric, written by `STABILITY_BUILDER`, last in `MODEL_BUILDERS` because it reads every table above through the engine. Columns: `season` (the latest season played when it was measured; the rows of the highest are the ones read), `game_type` (`regular`), `metric_id`, `through` (the last completed season measured, the one before the season in progress), `year_to_year`, `pairs`, `split_half`, `half_pairs`, `prior`, `reliability`, `first_season`, `last_season` and `reason`.

- **Year to year:** Pearson r between a player's (or team's) values in consecutive qualified regular seasons, pooled across positions (`nba-data-sources.md` measures what pooling adds), reported from 50 pairs (`MIN_PAIRS`).
- **Split half:** r between the odd and the even games of each qualified season by date, the player's (team's) own games, each half qualified at half the sample, stepped up to a season by Spearman-Brown. Only for a metric the engine reads by game; a state (SRS) and a table at season grain (published, composites) have none.
- **Prior:** for a rate, the sample at which it is half signal, k = n × (1 − r) / r with r the halves' raw correlation and n their median sample, in the metric's own sample unit (field-goal attempts, minutes, possessions). It is what `shrunk` gives the league.
- **Reliability:** from the year-to-year r: high at 0.6, medium at 0.35, low below, the template's thresholds (why they stand is in `nba-data-sources.md`).
- **What is measured:** every metric the engine reads at the season grain, each over its own coverage, through the engine itself (`compileQuery` with `internal: { unlimited, halves }`, the internal `half` dimension), so each value is exactly what a screen reads. A count is measured per game, a rate as it is. A player row qualifies by the metric's own sample and by the leaderboard's 1,000 minutes over 82 games, both scaled to the season's games; a team always does.
- **What is not, and why** (`reason`): gone from the source; published for one season at a time (DARKO); a rating as of a game for players; a forecast (`team_forecast`, `OUTCOME_TABLES`), whose value at a season's end is the outcome (odds of 100 % or 0 %, the record, the seed, a constant number of runs); fewer than two completed seasons in its coverage; fewer than 50 pairs; no spread (quadruple doubles, games left at a season's end); no value at a season's end (SOS left); and the engine's own reason, such as team hustle's "Published without games played.", where no team season ever qualifies.
- **When:** measured again only when its rows do not stand: the builder's version (its own number times a million plus `catalogueSignature`, a hash of every metric's formula, sample, minimum and table, so a new or changed formula measures again and new words do not), a completed season whose data changed (`ctx.changed`), or a season completed since (`through` moved). `seasons` returns the latest season played whenever anything changed, and `build` returns null when nothing it reads did, so a daily refresh of the season in progress keeps the rows.
- **Batches:** metrics of the same entity, transform, table and first season, 40 a query (39 and the qualifier for players), about 130 queries for 1,452 metrics, each reading only the columns the measure needs: carrying every column of every row back took 2 s a batch, the SQL 50 ms.
- **Read:** `readStability` in the service, once, kept until a refresh ends. `catalogueInfo` adds each metric's `stability` to the catalogue the renderer loads, so a column head costs no query; `priorsOf` gives `shrunk` its priors.

**Speed:** on a real refresh of a fresh copy of the Stage 9 gate load with all six builders, the models step computed every season in 168.3 s (372,222 rows, peak memory 1.8 GB). Each builder's compute over every season, timed apart on the same copy (the rest of the step is writing the rows): team strength 1.0 s, box-score composites 3.5, Elo 0.7, adjusted ratings 2.6, the season forecast 57.4, stability 37.7 (1,452 metrics). Stability measured again alone (a new version of its builder) in 38.4 s. A daily refresh with 2026-27 changed ran the models step in 3.5 s, the forecast's simulation of the season in progress most of it, the stability rows kept. Checked by `scripts/check-stability.mjs` (in [nba-data-sources.md](nba-data-sources.md), "Metric stability").

| `player(id)`                                     | Name, seasons, latest position and team; number, size, birth date and school from the latest roster line, read from the attribute tables (D51)                           |
| `games(season)`                                  | Every game on the schedule, played or not: its type, sides, score, whether a box score is held, overtimes                                                                |
| `game(id)`                                       | ESPN's venue, city, attendance and note, and the score by period when those add up to the final score                                                                    |
| `standings(season)`                              | The published standings: `src_nba_standings`, or the dashboards' file for 1995-96                                                                                        |
| `matchups(id, season)`                           | Who a defender guarded and who guarded them, from `pub_matchup_pairs`                                                                                                    |
| `lineups(team, season, type, group)`             | A team's five-man units for a season and season type with one dashboard's columns, most minutes first, from `pub_lineups`; empty before 2007-08                          |
| `profile(id)`                                    | The latest roster line and the draft pick, from the attribute tables (D51), and every combine the player went to, each measure with its percentile in its position group |
| `availability(ids)`                              | Each player's status on their team's newest official injury report that lists anyone, with its reason and date                                                           |
| `onCourtUnits(team, season, scope, size)`        | A team's groups of two to five players on the floor, counted from the plays, from `unit_game`: see "On court"                                                            |
| `withOrWithout(player, teammate, season, scope)` | A player's team with a teammate on and off the floor, in the games both played: see "On court"                                                                           |
| `coaches(team, season)`                          | The head coach and the assistants of a season, from `src_nba_coaches`                                                                                                    |
| `attributeValues(attribute, seasons)`            | The values a text attribute holds in those seasons, each with how many rows hold it, most first, at most 3,000: the Filters control's lists (T1701.2)                    |

- **A side with no row in `team`** is an All-Star team or a touring club: its name comes from the NBA's schedule, then ESPN's.
- **Overtime** is read from the team's minutes, five players over regulation (240 in the NBA) and five more per overtime minute (25 a period), from the league's `gameMinutes` and `overtimeMinutes`. It matches ESPN's period on nearly every game, and in 2001-02 ESPN's undercounts: it has 30 overtime games to the box scores' 70. Where `game` holds its own count (the WNBA's, T1301.5) it is read from there, NULL where neither the game logs nor ESPN knows it (most games of 1997 to 2001), rather than guessed from players' whole minutes.
- **Per league** (T1301.6): the roster and draft reads take whichever of the league's files is there (`src_nba_rosters` or `src_wnba_rosters`, the same columns), a team is joined on `abs(team_id)` in its season so the 2026 Portland Fire's rows reach their key (`-1611661327`), and a draft's year is the league's `eventYear` (the WNBA labels its draft by its own year). The standings read the dashboards' file in the WNBA, the only one before 2026.
- **The combine** (Plan T708) is read from four of its five tables, joined on season, id and name (`-1` stands for several players without an id). `draftcombinestats` repeats them column for column. The 46 measures are listed in `src/shared/stats/profile.ts`: measurements, four proportions worked out from them (wingspan and standing reach over barefoot height, and standing reach plus each vertical), athletic testing, and the shooting drills, each spot with makes and attempts and a total per distance. A percentile ranks a measure among every attendee of the same position group at every combine in the data, linked to an NBA player or not: the first listed position (`SG-SF` is a guard, as in Plan T504), mid-rank so tied players share the middle of their ranks, the faster time higher. Measurements have no better side, so they get a percentile but no rank. A test is held at a combine when anyone has a result in it; a player with no result in a held test reads blank, never 0. Shooting is made over attempted, rebuilt from its parts; the published percentage agrees on every row compared. The read takes about 80 ms.

## Sync

- **When it runs:** at launch, and every 6 hours while the window stays open. One at a time. Not while paused, and a first load does not start without room for it: see the Data panel in [stats-screens.md](stats-screens.md).
- **Order (D21):** tier by tier: core, published, events, play by play. Inside a tier, files of all seasons first, then the newest season back. So the app is usable after the first tier, and a load cut short keeps the seasons people look at most.
- **What is due:**
  - A step that finished is not tried again within a day; a failed one after an hour.
  - Files of all seasons are checked daily.
  - The current season is checked daily until its last month is over (`seasonEnd(league, season)`: the first day after `seasonMonths.last` in the year of its label, 1 July for the NBA, 1 November for the WNBA), then weekly, as the prior season is.
  - A season that has ended is sealed once a file has not changed for two weeks (`SETTLED_MS`): by its Last-Modified as published, kept in `source_state.modified_at`, else by when Metis last saw its content change. A season two back and older is sealed when loaded, as before. A sealed season is never fetched again; a source's `version` bump fetches it again.
  - So the WNBA's season, played May to October, is refreshed daily through October; in November it is checked weekly until its files have stood two weeks, then sealed. The NBA's is daily until 1 July, and its label turns to the next season in August, which is checked daily before it starts.
- **Freshness:** each request carries the file's `etag`. A file that has not changed downloads nothing, and logs `unchanged`.
- **Downloads:** up to 4 at once, ahead of the file being loaded, with 3 retries and growing waits on throttling, server errors and dropped connections. The client calls itself `Metis`. Files go to `<userData>/stats-tmp` and are deleted once loaded.
- **Loading:** one file at a time, each in one transaction, so a failed load keeps the old rows. A file not published (404) is `skipped` and tried the next day.
- **Quitting:** closing the worker aborts downloads and interrupts the running statement, and the step is logged `interrupted`. That is not an attempt, so the next run tries it again. Steps a crash left `running` are marked `interrupted` on the next open, and stale temp files are cleared.

Each file is one step, logged as `stats:<source>:<season>` (or `stats:<source>` for a file of all seasons) in the file's own `sync_log`. `source_state` holds what each source has per season: rows, size, etag, when it was fetched and whether it is sealed.

## Leaving a source out (Plan T1107)

A source family can be left out of a build. `LEFT_OUT_RELEASES` in `src/main/stats/sources.ts` lists release tags, named exactly (`nba_stats_synergy`, `nba_player_impact`). Every NBA and WNBA release loads; the list holds ESPN's college play by play (`espn_mens_college_basketball_pbp`, `espn_womens_college_basketball_pbp`), which no metric reads (D42). There is no setting for it: listing a tag is a one-line change and a release.

**The NCAA switch (D41).** `NCAA_STATS_LEFT_OUT` in the same file adds the 26 stats.ncaa.org releases (`NCAA_STATS_RELEASES`, 13 a side) to the list, so both college leagues ship and run on ESPN's tables and the dataset's ids, groups and models alone. None of them is a key release (the college keys are ESPN's schedules and player box scores, the crosswalk and the groups), so the list builds. Tested in `tests/main/stats/ncaaLoad.test.ts`: the refresh drops what they had loaded and downloads only the rest.

**What then happens** (`src/main/stats/leftOut.ts`):

- **Downloads:** the tag's files are neither downloaded nor checked for freshness.
- **The next refresh:** it drops the source tables every file of which is left out, and forgets their files in `source_state`, logged as one `stats:left-out` step. It marks the identity, game, published, play and model tables out of date, so each step rebuilds from what is left. A missing source reads NULL in every builder, so nothing fails, and an install that had loaded the tag ends up as one that never did. Later refreshes have nothing to drop and rebuild nothing for it.
- **Metrics:** one that reads the tag answers null with "Not included in this version.", whatever the season or filter. That covers a published metric whose table's source is left out, a metric on a built table (`GameTable.sources`), and any metric under a split once the NBA's play by play is out. Box-score metrics always answer.
- **The Data screen** lists the tag as "Not in this version", with no files expected.

**Per league.** The list is one for every league: each tag names its league (`nba_stats_shots`, `wnba_stats_shots`), and `leftOutIn(list, sources)` gives a league's refresh its own tags, plus any tag no league loads, which is then refused.

**The limit:** six tags of the NBA and the WNBA, and four of each college league, can never be left out. The NBA's: `nba_stats_schedules`, `nba_stats_player_boxscores`, `espn_nba_schedules`, `espn_nba_player_boxscores`, `nba_groups` and `nba_crosswalk`. The WNBA's: `wnba_stats_schedules`, `wnba_stats_player_game_logs`, `espn_wnba_schedules`, `espn_wnba_player_boxscores`, `wnba_groups` and `wnba_crosswalk` (both schedules, the game logs, ESPN's player box scores, the crosswalk and the groups). Each college league's: ESPN's schedules and player box scores, its crosswalk and its groups (`espn_mens_college_basketball_schedules`, `…_player_boxscores`, `mbb_crosswalk`, `mbb_groups`, and the women's alike), marked `keys` until their builders exist (T1302.4). The game, team and player tables, and their keys, are built from them (D13, D28), and every other table is keyed to those. The set is read from what the identity and game-table builds need (`IDENTITY_NEEDS`, `DERIVED_NEEDS`), not typed twice, plus the files a league marks `keys` while its builders do not exist yet (the WNBA's, until T1301.5). A list naming one of them, or a tag Metis does not load, is refused: the refresh logs a `stats:left-out` error with a plain message and loads nothing, and a test checks the committed list. Leaving a whole source out (every `nba_stats_` or `espn_nba_` tag) would need those builds to work from one source, which they do not.

**What it does not cover:** reads beside the engine (the shot chart, matchups, lineups, a game's flow) show what the rebuilt tables hold, which is nothing, rather than the reason. Fouls drawn come from ESPN's play by play inside a table built from the NBA's, so with only `espn_nba_pbp` out they read what the table holds, not the reason. The first load's disk check still expects the full download.

## Measuring a real load

Build first, then point these at a scratch folder, never at the app's own data.

```bash
node scripts/load-report.mjs /tmp/metis-load /tmp/metis-load/report.json
```

```bash
node scripts/coverage-report.mjs /tmp/metis-load docs/reference/nba-coverage.tsv docs/reference/nba-coverage.md
```

Each source table against the raw files' own row counts, for a folder of downloaded files with one folder per release (`~/.cache/metis-dev/wnba-raw`):

```bash
node scripts/check-source-rows.mjs /tmp/metis-load ~/.cache/metis-dev/wnba-raw --league=wnba
```

```bash
node scripts/stats-sql.mjs /tmp/metis-load statements.sql
```
